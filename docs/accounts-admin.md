## Accounts, stats and leaderboard (M6)

- **Analytics tab** (admin panel, `AnalyticsView.tsx`): `GET /api/admin/analytics` (`stats/analytics.ts`, `buildAnalytics`, tested in `analytics.test.ts`) gives daily series for the last 90 UTC days (visitors, visits, new players, new accounts, games) and the headline periods (today, yesterday, 7 days and the 7 before, month to date, last month, 30 days and the 30 before), games per title, registered vs guests, returning visitors and games per visitor. Visits come from the new `ActivityDay` table (`userId`, UTC `day`, `visits`; migration `20261030000000_activity_days`): `UserStore.recordVisit` runs on every socket connect and counts one visit per 30 minutes; the history therefore starts when this was deployed (`trackingSince`). New players = `User.createdAt` (guests included), new accounts = `registeredAt`, games = distinct matches. The web shows hero numbers with the change against the previous period, an overview table, a tap-a-bar chart (metric chips, 7 / 30 / 90 days) and bars per game. Only people who connect with a socket are counted, not anonymous page loads. The admin tab's icon is red (`favicon-admin.svg`) so it is easy to tell from the game.

- The leaderboard's first, default button is **All**: `GET /api/leaderboard?game=all` (`ALL_GAMES` in `userStore.ts`) adds up played and won over every game, ranked by wins. Each row also has a **Win %** column (wins / played, one decimal).

- Guest play stays the default. Every guest already has a `User` row (JWT `sub` = id), so **registering upgrades the same row** (email + password hash, `isGuest=false`, token unchanged): everything recorded while a guest is kept, nothing is "uploaded".
- Server (`apps/server/src`): `auth/userStore.ts` (`UserStore`: Prisma + in-memory, accounts, codes, images, results, leaderboard, `mergeInto`), `auth/passwords.ts` (scrypt, 6-digit codes stored as HMAC), `mail/template.ts` (`codeMail`: the HTML code mail in the app's palette, one tile per digit, pixel-art key art attached inline as `cid:hero`; the PNG is `mail/art.ts`, base64 generated from `assets/sprites/brand/key-art-boing.svg` at 6x with a small Python rasteriser because the server is bundled into one file and mail clients block SVG; regenerate it when that art changes; the text part carries the same code for the log mailer and e2e), `mail/mailer.ts` (`MAIL_MODE=log` prints codes to the server log and, outside production, exposes `GET /api/dev/last-mail?to=` for e2e; `smtp` uses `SMTP_HOST`/`SMTP_PORT` (465 = TLS)/`SMTP_USER`/`SMTP_PASSWORD`/`MAIL_FROM` via nodemailer; `smtpUrlFrom` in `config.ts` builds the connection string and URL-encodes the credentials, `SMTP_URL` still works as an all-in-one override, and `MAIL_MODE=smtp` without a host refuses to start; SMTP has connect/greeting timeouts so a blocked port fails fast; **Render's free tier blocks outgoing SMTP (the owner's dashboard currently has `MAIL_MODE=smtp`; `brevo`, Brevo's HTTPS API, is the alternative that always works there)**: `createBrevoMailer` posts to Brevo's HTTPS API with `BREVO_API_KEY`, there are no inline `cid:` images there, so the artwork is loaded from `PUBLIC_BASE_URL/mail-hero.png` (`apps/web/public/mail-hero.png`, same PNG as `mail/art.ts`; left out when the URL is empty)), `http/accountRoutes.ts`, `stats/record.ts`.
- **Guests are never lost by "Switch player"** (`lib/players.ts`, `pages/SignIn.tsx`, `components/SwitchPlayerSheet.tsx`): a guest's token is the only thing that identifies it, so every guest session is also kept in localStorage `pogo.players` (max 8, newest first; registered accounts are not kept: they log in with a password). "Switch player" only forgets the active token; the sign-in screen lists **Continue as <name>** cards (`continue-as-<id>`, one tap restores, a 401 drops the entry) and a × (`forget-player-<id>`) whose confirm is **strong** unless a recovery link was saved (`recoverySaved`) and **soft** otherwise. For a guest the Switch dialog (`switch-dialog`, `data-severity` soft/strong, `switch-confirm`) is soft because the guest is kept on the device; it turns strong only if the device could not store it (private mode). **Sign-out reloads the page** (`App.tsx`) instead of swapping in place: the iPhone home-screen app did not show the keyboard on the sign-in page after an in-place switch (cannot be tested headlessly; check on a phone). **Recovery links**: `?recover=<token>` (`consumeRecoveryLink` in `lib/session.ts`, read before `restoreSession`) logs a device in as that guest; a guest copies their own link in Profile (`profile-copy-recovery`, "Save this player"), and an **admin** creates one for any guest in the admin panel (player sheet, Recovery link, `POST /api/admin/users/:id/recovery`, audit `recovery-link`, link built from `PUBLIC_BASE_URL` or the admin's origin). A recovered guest registers as usual (same row, stats kept) or merges into an account. E2E: `e2e/tests/switch-player.spec.ts`.
- An iPhone home-screen app once showed no keyboard in any field, even on a bare test page with no app code (so it was iOS / the web-app container, not POGO; **restarting the phone fixed it**. If it happens again: restart the phone, remove any hardware keyboard, re-add the icon from Safari). The audio unlock in `App.tsx` ignores taps in text fields because starting audio while the keyboard opens may drop it on iOS.
- Flow: `POST /api/account/register/start {email}` (guest token) → mail with code (10 min, 5 attempts) → `register/verify {email, code, password}`. `POST /api/auth/login`, `reset/start`+`reset/verify`, `POST /api/account/merge {guestToken}` (moves a device guest's results into the account; only ever absorbs a guest), `DELETE /api/me {password}`, `GET /api/me/stats`, `GET /api/leaderboard?game=` (registered users only; Yatzy by best score, others by wins). Per-route limits are multiplied by 100 outside production (`limitScale`).
- Results: `Room` calls `deps.onGameFinished({gameId, matchId, results, humans, players, bots})` once per game (`matchId` = room code + game number, so rematches count separately); `app.ts` records one `GameResult` row per human (bots skipped; idempotent per user+match). Games vs the computer and solo games count too (`players`/`bots` columns).
- Pictures: `PUT /api/me/avatar` (registered only; raw `image/jpeg|png|webp` body ≤ 80 KB, magic bytes checked) stored in Postgres (`UserImage`, no disk on Render); the client crops/resizes to 256px first (`resizeImage` in `lib/session.ts`). The user's `avatar` string becomes `img:<userId>:<version>`; `AvatarFace` (`components/AvatarFace.tsx`) renders it (served by `GET /api/users/:id/avatar`, immutable cache) or the emoji. `PATCH /api/me` accepts the unchanged `img:` value so renaming keeps the picture. Rooms hold the user loaded at connect, so a new picture shows in rooms after a reconnect.
- Web: Home header buttons: leaderboard (`LeaderboardSheet`), profile (`ProfileSheet`: name, icon grid, register / login / reset / merge / delete steps, picture upload), settings. Guests see `RegisterNudge` ("Wow, great score! Keep track?") under their results (`ResultsPanel` `account` prop; Shell owns the sheet it opens). `SignIn` has "Have an account? Log in". Test ids: `account-register`, `register-email|send|code|password|submit`, `login-email|password|submit`, `signin-login`, `account-email`, `account-logout`, `register-nudge`, `nudge-register`, `merge-yes|no`, `leaderboard`.
- Tests: `apps/server/src/http/accounts.test.ts`, `e2e/tests/accounts.spec.ts`. Prisma migration `20261022000000_accounts`.


## Admin panel, roles, bans and the (dev) tag

- **Roles** (`packages/shared/src/protocol/roles.ts`): `PublicUser.role` = `user` (default, absent) | `moderator` | `admin`, plus the separate boolean `isDev`. `displayName(user)` = nickname + " (dev)" for developers; the server uses it for everything other players see (room member lists, game seats, chat, open-games host, leaderboard), while `PublicUser.nickname` stays plain (profile editing, tests). Staff need a registered account (they log in to the panel with email + password).
- **First admin**: env `ADMIN_EMAILS` (comma separated; `docker-compose.yml`, `.env.example`, `render.yaml`): at start-up, and whenever such an email registers or logs in, the account becomes admin (`withBootstrapRole` in `accountRoutes.ts`, loop in `app.ts`). After that, admins manage roles in the panel.
- **Developers**: env `DEV_EMAILS` (comma separated; compose, `.env.example`, `render.yaml`, local `.env`): these accounts become admin **and** `isDev` on every start-up and whenever they register or log in. The tag travels as the plain suffix `DEV_TAG` (" (dev)") in `displayName`; the web draws it as an animated rainbow "dev" through `PlayerName` (`components/PlayerName.tsx`, `splitDevTag`, CSS `.dev-tag`, still when reduced motion). Use `PlayerName` wherever a name is rendered as JSX; plain-text spots keep the literal suffix. The account must exist (register once), then set `DEV_EMAILS` in `.env` and restart.
- **Titles (prefix / suffix)**: a developer (`isDev`, not just admin) can give any **registered** player text before and after their nickname (paid perks or fun): `User.prefix` / `User.suffix` (Prisma migration `20261024000000_titles`), `PublicUser.prefix/suffix`, max `TITLE_MAX` (14) characters each, one line. `displayName` builds `prefix nickname suffix` plus the (dev) tag, so every place that already shows the display name (rooms, chat, leaderboard, seats) shows the titles after the player's next join/connect (rooms hold the user loaded at connect); the nickname itself stays editable by the player. API (dev only, 403 otherwise, logged in the audit log as `titles`): `POST /api/admin/users/:id/titles {prefix, suffix}` (empty = remove; guests refused). Web: `TitlesEditor` inside the player sheet of the **Players** tab (`AdminApp.tsx`, shown when `me.isDev` and the player is registered: live preview, tap-to-fill ideas, Save / Remove both). **Players tab**: **everyone** by default, guests (unregistered) included (`GET /api/admin/users?q=`, `&registered=1` for registered only; up to 200 rows, newest connection first); admins also see the last IP (`AdminUserRow.lastIp`, set by `touch` on every socket connect); chips Registered / Everyone / Guests, Online and Staff filters and a sort (last seen, newest, name), all client-side on top of the search box. **Settings shortcut**: developers see an "Admin panel" button (`settings-admin`) in the game's Settings; `openAdminPanel()` (`lib/session.ts`) copies the game token into `pogo.admin.token` and opens `/admin`, so there is no second login. **Account events in the Log tab** (`note()` in `accountRoutes.ts`, needs `moderation` in its deps): `register-requested`, `email-sent` / `email-failed` (with the MAIL code), `registered`, `login`, `login-failed`, `reset-requested`, `password-reset`; the address is masked (`ab***@host`). Test: `admin.test.ts` "titles (developers only)" and "account events in the log". After changing `schema.prisma` regenerate the client in the typecheck container: `docker compose run --rm --no-deps -w /app server sh -c "pnpm --filter @pogo/server prisma:generate; pnpm typecheck"` (a plain `make typecheck` uses a fresh volume with a stale client).
- **Powers**: moderator = search players, kick from a room, ban for up to 7 days (`MODERATOR_MAX_BAN_MINUTES`), lift bans, see rooms and the log; admin = also permanent bans, set roles (`POST /api/admin/users/:id/role`), give/remove the dev tag, see emails. Nobody can act on themselves or on someone of the same or higher rank (`target()` in `adminRoutes.ts`); guests cannot be given staff roles.
- **Server** (`apps/server/src`): `http/adminRoutes.ts` (`/api/admin/me|users|rooms|bans|audit`, `users/:id/kick|ban|role|dev`, `DELETE bans/:id`), `admin/moderation.ts` (`ModerationStore` Prisma/memory for `Ban` + `AuditLog`, `BanList` = in-memory index loaded at start so checks never hit the database, `banMessage`), `UserStore` additions (`search`, `setRole`, `setDev`, `touch`, `lastIpOf`; `User.lastIp/lastSeenAt` are updated on every socket connect), `RoomManager.evict/listAll/roomCodeOf`. Prisma migration `20261023000000_admin`.
- **Ban enforcement**: an `onRequest` hook in `app.ts` answers 403 `{banned: true, error}` to any `/api` call with a banned account's token; guest signup and login also refuse a banned IP (login: except staff, so an admin cannot lock themselves out); the socket handshake refuses a banned account or IP with `Error('banned')` (`data.message`), and banning disconnects the player's sockets and removes them from their room. A ban stores the IP the player last used when "block IP" is ticked (default). The web app shows the reason (`restoreSession` throws it; `useRealtime` returns `banned`, `Shell` renders a Banned screen and stops reconnecting).
- **Web** (`apps/web/src/admin`): `AdminApp.tsx` (login, tabs Players / Rooms / Bans / Log, a `Sheet` per player with kick, ban duration + reason + IP checkbox, role select and dev toggle), `adminApi.ts` (own token key `pogo.admin.token`). `main.tsx` renders it instead of the game when `isAdminSite()`: the hostname starts with `admin.` **or** the path starts with `/admin`, so `/admin` works on localhost and on the live address without any DNS.
- **Subdomain on Render**: add `admin.<your domain>` as a second custom domain of the same web service (Render dashboard, Settings, Custom Domains) and create the DNS CNAME it asks for; the single service serves both hosts (the SPA fallback returns the app for any path) and the panel appears because of the hostname. Cookies/localStorage are per origin, so you log in separately on the admin host.
- Tests: `apps/server/src/http/admin.test.ts`; `e2e/tests/admin.spec.ts` (runs only when the server has `ADMIN_EMAILS=admin-e2e@example.com`; it also needs `MAIL_MODE=log` because it registers through the dev mailbox, as `accounts.spec.ts` does: with `MAIL_MODE=smtp` in `.env` those e2e tests cannot read codes).

## Match history

- The last ten games of a player: `GET /api/me/history` -> `{history: MatchHistoryEntry[]}` (newest first; `UserStore.history`). Stored in `GameResult.summary` (JSON, migration `20261029000000_match_history`): `{players: [{id, nickname, avatar, bot, rank, score}], detail}`. `Room.reportFinished` passes the roster (computers too) and `GameDefinition.matchSummary(state)` (the game's own facts: Pet Match gives the arena, the moves and each player's pets and hit points) in `FinishedGame.roster|detail`; `stats/record.ts` builds the summary. Older rows have no summary (just the game and the date). After the migration regenerate the Prisma client in the running dev server (see `docs/friends.md`).
- Web: the trophy button opens a sheet with two tabs, **Leaderboard** (default) and **Match history** (`board-tab-history`, `MatchHistory.tsx`): per game the logo, when (`timeAgo`), Won / Lost / #n, every player with rank, picture, name and score (`GameUi.scoreText`, e.g. "45 HP"), and `GameUi.historyDetail` (Pet Match: the arena and everybody's pets). Guests have a history too (their results are kept).

## Admin panel: overview, matches, chats

- Tabs: **Overview** (default: online now, rooms (lobby / playing), registered players and guests, games in 24 h and this week, per title; `GET /api/admin/overview`), Players, **Rooms** (host, when created, messages, people watching, who is away; tap a room to read its chat), **Matches** (`GET /api/admin/matches?game=`: every finished game of everybody, newest 100, who played with rank and score, the game's own facts under "Game details"), **Chats** (`GET /api/admin/chats?room=&user=&q=`: the latest 500 room messages of all rooms from `admin/chatLog.ts`, in memory only, searchable by word / name / room code; private messages are never shown), Bans, Log.
- A player's sheet has **Matches** (`GET /api/admin/matches?user=`) and **Chat** (their latest room messages) next to Kick / Ban / Role. All of these are for staff (moderators too). Tests: `admin.test.ts` 'admin overview, matches and chats'.
