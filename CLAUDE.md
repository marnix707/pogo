# Pogo

Mobile-first multiplayer game hub (Plato-style): quick turn-based games with friends/strangers plus chat. First game: **Yatzy** (use "Yatzy" in the UI, never "Yahtzee"). Games are plug-ins; the core server/room/chat code must contain **no game-specific code**.

## Stack

TypeScript (strict) everywhere · pnpm workspaces · React 18 + Vite + Tailwind (PWA later) · Node 20 + Fastify + Socket.IO · PostgreSQL + Prisma · Zod for every inbound message/request · Vitest (unit) · Playwright (e2e, M4+) · ESLint + Prettier.

## Layout

```
apps/web        React/Vite client (dev server proxies /api and /socket.io to the server → one origin for phones)
apps/server     Fastify REST under /api + Socket.IO on the same HTTP server; Prisma in prisma/
packages/shared Types, Zod protocol schemas, GameDefinition interface, pure game logic (games/<id>)
docker/         Dev entrypoints   scripts/  Host helper scripts
```

Game plug-in split: pure logic in `packages/shared/src/games/<id>`, UI in `apps/web/src/games/<id>`, logic registry in `packages/shared/src/games/registry.ts` (`getGame(id)`), UI registry in `apps/web/src/games/registry.ts`. Rooms only see `GameDefinition` (createInitialState, validateMove, applyMove, getPlayerView, getCurrentPlayers, isGameOver, getResults, optional autoMove). Randomness is always an injected `Rng` (server: `crypto`; tests: `createSeededRng` / scripted `createDiceRng` from shared). `autoMove` is called repeatedly by the server until the timed-out player is no longer to move.

## Yatzy (packages/shared/src/games/yatzy)

Moves: `{type:'roll', held:boolean[5]}` (holds are sent with the roll; ignored on the first roll) and `{type:'score', category}`. Standard Joker rules: with Yatzy box filled, a further Yatzy forces the matching upper box, else any open lower box (full house/straights at full value), else any upper box for 0; +100 only if the Yatzy box holds 50. `getPreviewScores` drives the UI score preview.

## Realtime server (apps/server)

- `buildApp(deps)` in `src/app.ts` wires Fastify + Socket.IO + `RoomManager`; `index.ts` injects Prisma user store, crypto Rng and config (`loadConfig`). Tests inject an in-memory user store and seeded Rng.
- Identity: `POST /api/auth/guest {nickname, avatar}` → `{token, user}` (JWT, 90d; client keeps it in localStorage key `pogo.token`); `GET/PATCH /api/me`. Sockets authenticate with `auth: {token}` in the handshake.
- Rooms (`src/rooms`): `RoomManager` (code → `Room`, one room per user) and `Room` (members, settings, lifecycle, timers). They only use `GameDefinition`; tests use a fake game (`rooms/testGame.ts`) to prove it.
- Protocol (`packages/shared/src/protocol`): client emits `room:create|join|leave|kick|settings|start|rematch` and `game:move` with Zod-validated payloads and an ack `Result`; server pushes `room:state` (per-player filtered `RoomView`, or `null` + reason when you are no longer in a room) on every change and on (re)connect.
- Presence: a user is connected while ≥1 socket is open. Lobby: disconnected members are dropped after `DISCONNECT_GRACE_SEC`. In game: seat is kept; with a turn timer, if every current player is absent for the grace period (with unlimited time (`turnTimeSec` 0) nothing is ever auto-played for people who are merely disconnected; only players who left the room are still played for), or the turn timer (`TURN_TIME_SEC`, default **0 = off**; per-room `turnTimeSec`, 0 = off) runs out, the server auto-plays via `autoMove` (multi-step turns are paced ~1.2s apart). Rooms nobody is connected to are deleted after `ROOM_TTL_SEC`.
- Clock hooks on `GameDefinition` (all optional): `isFreeMove(move)` (a move that does not restart the turn clock), `keepsClock(before, after)` (the clock keeps running across the move: Karma's card swap has **one deadline for the whole phase**, started when the phase starts; no swap/Ready by anybody, computers included, resets it, and at the deadline everybody who is not ready is played by `autoMove` so the game starts), `clockBonusMs(state)` (extra time when the clock starts: Karma adds `rulesIntroMs(rules)` while the clients play the rules intro, so the swap time starts after the animation, during the tutorial). `Room.clockKept(before)` applies `keepsClock` in `move`, `autoplay` and `playBots`.
- **Playing alone**: a lone solo game (nobody else in the room, no computers, a game with `minPlayers` 1, i.e. Yatzy) has **no turn timer by default** (`Room.turnTime`: the effective timer; `RoomView.turnTimeSec` shows it, so the lobby's timer buttons read Off); once a second player joins the normal default (`TURN_TIME_SEC`, now 0 = off, so every lobby starts with the timer Off) applies again. A timer somebody picked explicitly (`turnTimeChosen`: `room:create {turnTimeSec}` or a `room:settings` change) is always used as picked. Karma etc. keep their default.
- Rate limiting: REST via `@fastify/rate-limit`; sockets via a per-socket token bucket (20 burst, 10/s).
- Share links look like `/?join=CODE` (handled by the web shell after sign-in).

## Error codes (troubleshooting)

- Every error shown to a player has a code behind the text: "Room not found (ROOM-101)". Unexpected server errors read "Something went wrong on our side (SYS-500 · ab12cd)": the 6-letter **ref** is also in the Render log line of that request (`ref`; for REST it is the request id, for sockets `newRef()`), so a screenshot is enough to find the cause. Anything not in the catalogue shows `SYS-000`.
- The catalogue is `packages/shared/src/protocol/errors.ts` (`KNOWN_ERRORS`: exact message or regex -> `AREA-NNN`; areas NET, SYS, MAIL, ACC, ADM, ROOM, GAME, YAT, KAR, LAST; 1xx = not allowed / the player's side, 5xx = ours). **To add an error: add its message to `KNOWN_ERRORS`**; `apps/server/src/errors.test.ts` scans the source for `error:`/`fail(`/`err(` string literals and fails for any message without a code. `failResult()` (used by `fail()` in `Room`/`RoomManager` and the socket handler) and a Fastify `preSerialization` hook in `app.ts` attach `code` to every socket ack and REST error body; the web shows `formatError(error, code, ref)` (`Shell` toasts, `lib/session.ts`, `admin/adminApi.ts`).
- Server errors: `app.setErrorHandler` answers anything thrown with `{error, code: 'SYS-500', ref}` and logs it with `code`/`ref` (the raw error never reaches the player); `AppError(status, code, message)` (`apps/server/src/errors.ts`) reports a chosen coded error. **Mail**: a failing send becomes a 502 with the friendly text "We couldn't send the email. Please try again in a minute." and a `MAIL` code from `mailFailure()`: MAIL-001 other/provider down, **MAIL-002 the provider refused our login or API key** (Brevo 401/403, SMTP EAUTH: check `BREVO_API_KEY`, it must be an API key `xkeysib-…`, not an SMTP key `xsmtpsib-…`), MAIL-003 the provider refused the mail (bad sender or address, Brevo 400), MAIL-004 unreachable/timeout (SMTP ports are blocked on Render's free tier), MAIL-006 provider rate limit, MAIL-005 dev mailbox empty. The log line carries the real cause in `cause`.

## Deployment (Render free tier + Neon, Frankfurt)

- `render.yaml` Blueprint → one Docker web service (`Dockerfile`, multi-stage: prod deps + Prisma client, web build, esbuild-bundled server). The server serves the built web app (`WEB_DIST_DIR`) with SPA fallback, so it is a single origin (no CORS/proxy). `docker/start.sh` runs `prisma migrate deploy` (retrying while Neon wakes), then `node dist/index.js`.
- Secrets are set in the Render dashboard (`sync: false`): `DATABASE_URL` (Neon, `?sslmode=require`; pooled hosts also need `&pgbouncer=true`) and optional `DIRECT_URL` (Neon direct string for migrations; defaults to `DATABASE_URL`). `JWT_SECRET` is generated by Render.
- **Never put a `value:` on a setting the owner tunes in the Render dashboard** (mail mode/sender, filters, timings): every deploy writes `render.yaml` values over the dashboard, which once reset `MAIL_MODE` to `log` and silently stopped all mail. Those keys are `sync: false` (asked for once, never overwritten); only fixed technical keys (`NODE_ENV`, `SERVER_PORT`, `LOG_LEVEL`, generated `JWT_SECRET`) carry a value. The code has defaults for all of them.
- Render health check is `/api/livez` (no DB access, so probes don't keep Neon awake); `/api/healthz` also checks the DB.
- Production runs with `trustProxy` so rate limits use the real client IP; only `/api` is rate limited.
- Free-tier caveats: spins down after 15 min without traffic (~1 min cold start); in-memory rooms are lost on restart/redeploy; single instance only.
- Test the prod image locally: `docker build -t pogo-prod .` then run it on the compose network with `DATABASE_URL` pointing at a scratch database.

## Accounts, stats and leaderboard (M6)

- Guest play stays the default. Every guest already has a `User` row (JWT `sub` = id), so **registering upgrades the same row** (email + password hash, `isGuest=false`, token unchanged): everything recorded while a guest is kept, nothing is "uploaded".
- Server (`apps/server/src`): `auth/userStore.ts` (`UserStore`: Prisma + in-memory, accounts, codes, images, results, leaderboard, `mergeInto`), `auth/passwords.ts` (scrypt, 6-digit codes stored as HMAC), `mail/template.ts` (`codeMail`: the HTML code mail in the app's palette, one tile per digit, pixel-art key art attached inline as `cid:hero`; the PNG is `mail/art.ts`, base64 generated from `assets/sprites/brand/key-art-boing.svg` at 6x with a small Python rasteriser because the server is bundled into one file and mail clients block SVG; regenerate it when that art changes; the text part carries the same code for the log mailer and e2e), `mail/mailer.ts` (`MAIL_MODE=log` prints codes to the server log and, outside production, exposes `GET /api/dev/last-mail?to=` for e2e; `smtp` uses `SMTP_HOST`/`SMTP_PORT` (465 = TLS)/`SMTP_USER`/`SMTP_PASSWORD`/`MAIL_FROM` via nodemailer; `smtpUrlFrom` in `config.ts` builds the connection string and URL-encodes the credentials, `SMTP_URL` still works as an all-in-one override, and `MAIL_MODE=smtp` without a host refuses to start; SMTP has connect/greeting timeouts so a blocked port fails fast; **Render's free tier blocks outgoing SMTP, so production uses `MAIL_MODE=brevo`**: `createBrevoMailer` posts to Brevo's HTTPS API with `BREVO_API_KEY`, there are no inline `cid:` images there, so the artwork is loaded from `PUBLIC_BASE_URL/mail-hero.png` (`apps/web/public/mail-hero.png`, same PNG as `mail/art.ts`; left out when the URL is empty)), `http/accountRoutes.ts`, `stats/record.ts`.
- **Guests are never lost by "Switch player"** (`lib/players.ts`, `pages/SignIn.tsx`, `components/SwitchPlayerSheet.tsx`): a guest's token is the only thing that identifies it, so every guest session is also kept in localStorage `pogo.players` (max 8, newest first; registered accounts are not kept: they log in with a password). "Switch player" only forgets the active token; the sign-in screen lists **Continue as <name>** cards (`continue-as-<id>`, one tap restores, a 401 drops the entry) and a × (`forget-player-<id>`) whose confirm is **strong** unless a recovery link was saved (`recoverySaved`) and **soft** otherwise. For a guest the Switch dialog (`switch-dialog`, `data-severity` soft/strong, `switch-confirm`) is soft because the guest is kept on the device; it turns strong only if the device could not store it (private mode). **Sign-out reloads the page** (`App.tsx`) instead of swapping in place: the iPhone home-screen app did not show the keyboard on the sign-in page after an in-place switch (cannot be tested headlessly; check on a phone). **Recovery links**: `?recover=<token>` (`consumeRecoveryLink` in `lib/session.ts`, read before `restoreSession`) logs a device in as that guest; a guest copies their own link in Profile (`profile-copy-recovery`, "Save this player"), and an **admin** creates one for any guest in the admin panel (player sheet, Recovery link, `POST /api/admin/users/:id/recovery`, audit `recovery-link`, link built from `PUBLIC_BASE_URL` or the admin's origin). A recovered guest registers as usual (same row, stats kept) or merges into an account. E2E: `e2e/tests/switch-player.spec.ts`.
- An iPhone home-screen app once showed no keyboard in any field, even on a bare test page with no app code (so it was iOS / the web-app container, not POGO; **restarting the phone fixed it**. If it happens again: restart the phone, remove any hardware keyboard, re-add the icon from Safari). The audio unlock in `App.tsx` ignores taps in text fields because starting audio while the keyboard opens may drop it on iOS.
- Flow: `POST /api/account/register/start {email}` (guest token) → mail with code (10 min, 5 attempts) → `register/verify {email, code, password}`. `POST /api/auth/login`, `reset/start`+`reset/verify`, `POST /api/account/merge {guestToken}` (moves a device guest's results into the account; only ever absorbs a guest), `DELETE /api/me {password}`, `GET /api/me/stats`, `GET /api/leaderboard?game=` (registered users only; Yatzy by best score, others by wins). Per-route limits are multiplied by 100 outside production (`limitScale`).
- Results: `Room` calls `deps.onGameFinished({gameId, matchId, results, humans, players, bots})` once per game (`matchId` = room code + game number, so rematches count separately); `app.ts` records one `GameResult` row per human (bots skipped; idempotent per user+match). Games vs the computer and solo games count too (`players`/`bots` columns).
- Pictures: `PUT /api/me/avatar` (registered only; raw `image/jpeg|png|webp` body ≤ 80 KB, magic bytes checked) stored in Postgres (`UserImage`, no disk on Render); the client crops/resizes to 256px first (`resizeImage` in `lib/session.ts`). The user's `avatar` string becomes `img:<userId>:<version>`; `AvatarFace` (`components/AvatarFace.tsx`) renders it (served by `GET /api/users/:id/avatar`, immutable cache) or the emoji. `PATCH /api/me` accepts the unchanged `img:` value so renaming keeps the picture. Rooms hold the user loaded at connect, so a new picture shows in rooms after a reconnect.
- Web: Home header buttons: leaderboard (`LeaderboardSheet`), profile (`ProfileSheet`: name, icon grid, register / login / reset / merge / delete steps, picture upload), settings. Guests see `RegisterNudge` ("Wow, great score! Keep track?") under their results (`ResultsPanel` `account` prop; Shell owns the sheet it opens). `SignIn` has "Have an account? Log in". - Tests: `apps/server/src/http/accounts.test.ts`, `e2e/tests/accounts.spec.ts`. Prisma migration `20261022000000_accounts`.

## Public lobby & chat (M5)

- Rooms are `private` (default, join by code/link) or `public`. `Room.summary()` returns a `PublicRoomSummary` only for public rooms in `lobby` status that are not full; `RoomManager.listPublic()` sorts them longest-waiting first (cap 50). Clients call `lobby:subscribe` (joins the socket.io room `lobby`, ack = current list) and receive `lobby:list` pushes; `app.ts` debounces (150ms) and only pushes when the list actually changed. Subscriptions are lost on reconnect, so the web hook re-subscribes on `connect` (`watchLobby` in `lib/socket.ts`).
- `room:quickplay {gameId}` = join the longest-waiting open public room for that game (idempotent if you already wait in one), else create a public room.
- Chat is per room and in memory: `Room.chat()` sanitizes (`chatSendSchema`: one line, ≤300 chars), masks profanity (`maskProfanity` in `packages/shared/src/moderation`, a basic English+Dutch word list with leetspeak/boundary handling), keeps the last 100 messages and pushes `chat:message` to members; `chat:history` is sent on join/create/reconnect (it can arrive just before `room:state` on a refresh, which the web hook accounts for). Per-user flood limit in `socket/handlers.ts` (burst 5, then 1 per 2s) on top of the per-socket event limiter. Guest nicknames are also checked with `containsProfanity`. The whole filter is switched by the server setting `PROFANITY_FILTER=on|off` (default on; `maskText` is injected into the rooms, nickname refusal is in `authRoutes`). It is currently **off** in `render.yaml` (flip it in the Render dashboard under Environment) and in the local `.env`; the e2e tests read the same variable so they pass either way.
- **Only the game card is gold in the lobby**: the top bar (with its settings button), the settings blocks and the crew rows use `.calm` (`index.css`: the blue-slate panel tokens re-pointed inside the gold `.menu`), the chat is grey; `TileButton` takes a `className` for this.
- The chat box and its input are **grey** (`.chat-grey`, `index.css`: panel = the palette's light gray `#dcdcdc`, bubbles `196 200 210`, dark ink) instead of the gold menu boxes; the message list is 80 % opaque so the contour waves show through.
- Chat message layout (`ChatPanel`): a square icon tile (`Avatar size="chat"`, as high as the name line plus a one-line bubble: its bottom edge lines up with the bubble) on the outer edge of each message (left for others, right for mine), the bold name above the bubble (the pixel font has no bold weight, so `font-bold` is thickened with a 1px `text-shadow`).
- Web: `ChatPanel` (inline in the lobby, in a bottom `Sheet` during games with an unread badge on the header chat button), open games list on `Home`.

## Karma (the "Shithead" card game; packages/shared/src/games/karma, apps/web/src/games/karma)

- Implements the base rules from https://en.wikipedia.org/wiki/Shithead_(card_game): 2-5 players, one 52-card deck, 3 face-down + 3 face-up + 3 hand cards each, rest is the draw deck. Cards are numbers 0-51 (`suit = floor(c/13)`, `rank = c%13+2`, J=11..A=14).
- Phases: `swap` (everyone acts at once: swap a hand card with a face-up slot, then `ready`; hidden until all ready) → `play` → `over`. The starter holds the lowest ordinary card (4 up to ace; 2, 3 and 10 are specials and never start) among face-up cards and hands; equal ranks are decided by suit: clubs, diamonds, hearts, spades; only specials around = first seat (`findStarter`).
- Turn: play one card or a set of the same rank, equal or higher than the top card, from hand first, then face-up, then face-down (blind, one at a time); or `pickup` the whole pile (allowed even if a play exists). 2 plays on anything and anything plays on a 2. An **8 skips the next player** (`advance(..., skips)` in `game.ts`): each 8 in the played set skips one more active player, you can never skip yourself so with two players an 8 simply means you go again, a burn (10 / four of a kind) takes priority over skipping, a blind 8 skips too, a failed blind card never does, and the skipped ids are in `KarmaEvent.skipped` for the UI. After a 7 the next card must be **7 or lower** (3-7, so 7s stack on 7s), a 2 or a 10 (a "lower or equal" house variant; `canPlayRank` is the single source of truth, also used by the UI to dim cards). 10 plays at any time on anything (including after a 7) and burns the pile; four of a kind on top of the pile burns it too (played at once or completed over turns). After a burn the same player leads again. After every play the hand is refilled to 3 from the deck. A face-up card may always be tried: when too low it goes onto the pile like a failed blind card (`failed`, `mustPickUp`, then `pickup` takes the pile including it); hand cards must still be playable. A too-low blind card is turned over and lies on the pile (event `failed: true`, state/view `mustPickUp`): its owner's only move is then `pickup` (a separate move and event, so everyone sees the card first); `autoMove` and bots do it by themselves.
- Decisions where the article is silent: jokers are not used; **a 3 is invisible** (house rule, `effectiveTop` in `game.ts`: a 3 is always playable and the next play is measured against the topmost non-3 card, so 7, 3 still means "7 or lower"; a pile of only 3s counts as empty; the four-of-a-kind burn still looks at the physical top four cards). Other variants are not implemented (7 = "lower or equal" and 8 = "skip" are); a player who burns with their last card is out and play passes on; ranks are by the order players ran out, the last player left is the loser (`score = players - rank`).
- End of game (leftovers): when the game is over (`phase` `'over'`) `KarmaView.leftovers` carries what the player who is left still holds (hand + the real face-down cards; `null` earlier, so nothing leaks). The table is **not** cleared when the game ends (my dock stays; moves are impossible anyway) and the loser's cards turn over in place: face-down cards first, then the hand, on their seat (`Seat`/`TableSlots.revealDown`/`HandFan.faces`) or in my own dock when I am the loser, each a `FlipReveal` (back shrinks away, face grows in: `card-back-out`/`card-face-in` in `index.css`, instant with reduced motion). Timing is in `games/karma/reveal.ts`: the turning **starts when the game is really over**: after a last face-down card (which has its own win reveal) when that card has finished turning, i.e. when the confetti starts (`AFTER_LAST_CARD_MS` = `TURN_MS` + a beat; keep the two in step), otherwise 0.7 s after the last move; one card per `revealStep` (420 ms, quicker for a huge hand), each turn takes `REVEAL_FLIP_MS` (700 ms); `resultsDelayMs` holds the standings back until it is all done plus `REVEAL_HOLD_MS` (1.5 s).
- Privacy: `getPlayerView` gives each player only their own hand; face-down cards are hidden from everyone including their owner (the view only says which slots still hold a card); the deck is a count. The pile and face-up cards are public. `lastEvent` (seq, kind, cards, burned, pickedUp, out) narrates the latest move to every client.
- `autoMove`: swap = ready; otherwise lowest legal rank (specials 2/10 last, whole set of that rank; 1 time in 4 the second-lowest, see below), else pick up; blind = first remaining slot. It reports `endsTurn` by simulating the move, so a burn (same player again) is paced like Yatzy's multi-step turns.
- **Games can loop forever under deterministic play.** With the 7 rule (and 8 skips) a fixed "always play the lowest card" strategy can circle indefinitely, e.g. a 7 that nobody can follow is picked up and led again. Measured over 500 games per size: ~1 in 500 stuck for always-lowest sets, 4-6% for single-card plays, **0 in 2000 once there is a 25% chance of the second-lowest rank** (that is what `autoMove` and the e2e strategy do; `game.test.ts` runs 600 auto-played games to guard it). Any bot or test strategy for Karma must include randomness and play sets. Humans do not loop in practice; the room's absent-player auto-play and abandoned-room TTL bound the damage anyway.
- Card animation (FLIP, in `PlayingCard.tsx`): every card with a `flip={{id, origin?}}` prop records its on-screen box after each render (module-level `lastBoxes`, keyed by card id, cleared on resize); if a card's box changed (hand re-fan, swap between hand and face-up slot, hand -> pile) it slides from the old box with the Web Animations API (320ms). A card never seen before (drawn from the deck, picked up from the pile, an opponent's hand card landing on the pile) starts from an `origin` anchor (deck / pile / that opponent's seat). The outer element is what moves, and a card's remembered box is its _layout_ box (the running animation's transform is subtracted, otherwise re-renders mid-flight start bogus slides); deck/pile origins are points so cards grow out of them at their own proportions. The action column is the timer (2 parts) over the Play button (3 parts) filling everything to the right of my table cards, which sit at the left (the column is always shown; Play is only disabled off-turn, so the layout never bumps between turns). There is no Pick up button and no automatic pickup: when nothing in the active zone can be played (`mustPickUp`) the pile pulses (`.pile-pulse`) and ONE tap picks it up (a voluntary pickup is two taps). The cards of a multi-card play leave one after another (170ms apart, 520ms flights; `playFlight`, `delayMoves`) so you can see how many were thrown. The picked-up cards then fly from the pile into the hand one by one (`delay` in `FlipProps`, ~700ms total). Burns resolve instantly on the server, so the client keeps the played cards visible on the pile for `GHOST_MS` (1.1s; a four-of-a-kind burn instead plays the `FourBurn` overlay for `FOUR_BURN_MS`: table dimmed, four cards side by side, fire, fade; its fire carries `burn-flash`, `ghost` state; flame and fling wait for it); selection lift and pile tilt live on an inner element so they never count as movement. Animations are off for the first paint and when `prefers-reduced-motion` is set (`CardFlipContext`); **tests that tap cards must use reduced motion**, otherwise Playwright waits for each sliding card to settle.
- Card sizes are numeric (px per em, card = 5em x 7em): base sizes are my cards 14, pile 17.5, deck 13.4 (>= 20% bigger than the first version at every phone height; this was measured, see below); `useCardScale` = `clamp((viewportHeight - 238) / 442, 0.72, 1.12)` fits table + hand + opponents into the screen; opponents' fonts come from `seatFont` (11 / 9.6 / 8.2 / 5.7 for 1 / 2 / 3 / 4 opponents) and with 3+ opponents their columns overlap (`overlap` prop) so bigger cards fit a narrow seat; the hand is laid out by `lib/handLayout.ts` (`handLayout(count, width, baseFont)`, unit-tested): **cards overlap between 10% and 30%**: every card keeps at least `MIN_VISIBLE` (0.7, i.e. at most 30% overlap; the numbers to tweak) of its width visible, and a sparse hand spreads only until each card shows `MAX_VISIBLE` (0.9, i.e. at least 10% overlap; `SPREAD_PAD_PX` of free edge; `marginLeft = strip - cardW`), and when a row would show less, the hand wraps into another row; the fewest rows that satisfy it are used and they are balanced (`data-rows`); before a row is added the cards shrink continuously (a row may use cards down to `MIN_SHRINK` = 75% of its normal size so that, say, 6 cards still fit one row with at most 30% overlap); extra rows overlap the one above by half a card and their cards are capped smaller (`WRAP_SCALE` 85% for two rows, `MANY_ROWS_SCALE` 70% from three) so a big hand stays on screen. The deck + pile sit on the left of the table with the event/hint text and the Rules button to their right (this saved ~75px of height versus stacking the text underneath; if you change sizes, re-check that nothing overlaps at 600-860px heights with 2-5 players).
- Controls (`selection.ts`, `planTap`, unit-tested; **no timing anywhere**): **a card you hold once: tap selects it, tapping the selected card again plays it. A rank you hold two, three or four of: tapping any one selects them all, tapping a selected one drops just that card (tap once more to add it back), and the Play button plays the set (so even four of a kind is played with Play, no double tap). Tapping another rank replaces the selection, and tapping anywhere that is not a button (the table, a seat, the dock background; cards, Play, Ready and the pile are buttons) clears it.** Face-down cards: tap selects, tapping it again flips it. The swap phase has a **Ready button** (`karma-ready`, with the turn clock as a draining `TimerDrain` bar inside it that drains **vertically** (`vertical` prop, `.timer-drain-v`: the level drops from the top; all other clocks drain sideways)) and the three face-up cards float and glow (`float` prop on `PlayingCard`, CSS `.card-float` on a wrapper so FLIP boxes are unaffected; off with reduced motion); tapping one hand card and one face-up card swaps them. ## Karma game modes and rules

- **Endgame table cards**: when my hand and the deck are empty (`endgame` in `KarmaGame`) my table cards leave the top-left slot and are drawn in the hand row instead (`TableSlots spread`: only columns that still hold a card, centred, so two recentre; `egFont` fills the width), the timer + Play fill the whole top row, and when cards come back into my hand they slide back up. ## Last Card (the UNO-style colour-match game; packages/shared/src/games/lastcard, apps/web/src/games/lastcard)

- Standard rules, 108 cards (`cards.ts`: id 0-99 = four colours x 25 (one 0, two each 1-9, two each skip / reverse / draw two), 100-103 wild, 104-107 wild draw four; `cardInfo`, `canPlayCard`, `cardPoints`), 2-6 players, 7 cards each, the game starts on a number card (action cards are buried), random first player. Play a card of the current colour or the same number/symbol; wilds always, **Wild Draw Four only without a card of the current colour** (enforced, there is no challenge). Skip skips, reverse flips `direction` (with two players it is a skip), draw two / draw four make the next player draw and lose the turn (no stacking). Nothing to play: `draw` one card; if it fits it is `state.drawn` and may be played or `pass`ed, otherwise the turn ends by itself. The discard pile is reshuffled into the deck when it runs out. First out wins (`state.winner`); the others are ranked by the points in their hand (number value, action 20, wild 50), ties share a rank; scores are hidden (`hideScores`).
- **UNO! and call-outs** (the reference site's rule): call UNO! **right before** (`uno: true` on the `play` that leaves one card; the button can be *armed* with two cards) or **right after** (`{type:'uno'}`) playing the second-to-last card. A `play` that leaves one card without the flag opens `state.callWindow = playerId`; the window closes on that player's `uno`, on a `callout`, or on the **first draw / pass / play by anybody** ("the next player started"): then nobody is punished (`uno` after that is refused, "Too late"). While it is open **any other player** may send `{type:'callout', target}`: the target draws **4** cards (`event.kind 'callout'`, `victim`, `state.catchCall {seq, byId, targetId}` kept apart from `lastEvent` like `unoCall`); both moves are allowed out of turn and are *free moves* (no clock restart). **You cannot finish with a special card** (action or wild): `validateMove` refuses it, you must draw. Computers always call UNO! with the play, and `autoMove` calls out a forgetful player 85 % of the time (`CALLOUT_CHANCE`, `endsTurn: false`); `settleMs` is 2.2 s while a window is open, so computers never act before a human could press UNO! or catch somebody. The client additionally **holds** everybody (cards, draw, pile; `CALL_HOLD_MS` 1.5 s, local) when somebody else is in the window. A 300-game auto-play test guards against endless games and lost cards.
- State/view: `LastCardState` (players with `called`, `stock`, `pile`, `color`, `turn`, `direction`, `drawn`, `winner`, `lastEvent`, `unoCall {seq, playerId}`: the latest call is kept apart from `lastEvent` so the next move cannot hide the announcement). `LastCardView` shows my hand, the others' counts and `called`, the top card, up to three cards below it, `mustCall` (I hold one card and have not called).
- Web (`apps/web/src/games/lastcard`): `LastCardGame.tsx` (seats clockwise from me with a yellow background for the player on turn and a red UNO! badge / pulsing "1 card…" for a single card, draw pile + discard pile on a ring in the current colour with the direction arrow, event line `lastcard-event`, my hand fanned to fit (scrolls when huge), Draw / Pass button carrying the turn clock, the **UNO! button** `uno-button` with `data-state` = `urgent` (one card, pulsing red) / `armed` (two cards on my turn: tap arms it, the next card is played with UNO!) / `idle`, wild colour picker `lastcard-color-picker`, the **announcement** `uno-called` (big "UNO!" + who called it, 1.9 s, for everybody, not for a call made before joining; keyframes `lastcard-call` in `index.css`, fade only with reduced motion)). One tap on a playable card plays it (unplayable ones are dimmed and explain why in the event line). Test ids: `lastcard-game`, `lastcard-card-<id>` with `data-playable`, `lastcard-top`, `lastcard-draw`, `lastcard-draw-button`, `lastcard-pass`, `lastcard-seat-<id>`, `lastcard-color`, `lastcard-direction`. E2E: `e2e/tests/lastcard.spec.ts` plays a whole game against two computers.
- **Card sizes and hand** = Karma's: `useCardScale(LASTCARD_CHROME)` (`lib/cardScale.ts`, chrome 300px; Karma uses 238) gives `myFont = 18 * scale`, `pileFont = 19.5 * scale`, `stockFont = 14.5 * scale`, and my hand is laid out by `handLayout()` (`lib/handLayout.ts`, shared with Karma: 10-30 % overlap, shrinks to 75 % before another row, extra rows overlap by half a card, `data-rows`). Overlapped cards intercept a centre click: tests tap the left strip (`STRIP` from `karma-helpers.ts`).

## Computer players (bots)

- A game opts in with `GameDefinition.supportsBots` (Karma and UNO; Yatzy's `autoMove` is too basic and it has a solo mode anyway). Bots are ordinary seats in the game state: ids `bot:1..n`, names from `BOT_NAMES` (skipping names people in the room use), avatar `robot` (`packages/shared/src/game/bots.ts`). They are **not** room members for auth/chat/kick/capacity purposes (`Room.hasMember`, `memberCount`, `activeMemberIds` exclude them) but appear in `RoomView.members` with `bot: true` so the UI can name them.
- Room setting `bots` (create, `room:settings`, `RoomView.bots`). Seats are added in `Room.start()` after the people and removed on rematch (the setting stays). `room:create {gameId, bots, autoStart: true}` is the one-tap "Play the computer" flow (private room, starts at once). Total seats must fit `game.maxPlayers`; joining people count against `memberCount + bots`.
- Driving them: `Room.botDue()` / `playBots()` wake the room `botMs` after the last state change (env `BOT_DELAY_MS`, 700 in dev compose, 1000 default) and every bot that is up makes one `autoMove`. They pause while no person is connected, a room with no people closes immediately (`afterMembershipChange`) or after the TTL, and no clock is shown (`deadline: null`) while only bots are up. Bots never see anyone's private cards: they use the full server state like `autoMove` for absent players, and clients still only receive `getPlayerView`.
- Quality: Karma's `autoMove` swaps strong cards (10, 2, aces, kings...) face-up with `bestSwap` (a swap must gain >= 2 `tableValue`), then plays lowest-rank-first with a 25% second-lowest jitter. It is deliberately easy-ish; there is no difficulty setting yet.
- Web: the lobby has a "Computer players" stepper and a "Start vs computer" button; Karma seats of bots show "CPU ·". Tests: `RoomManager.test.ts` (fake timers, a whole game vs 2 bots), `app.test.ts` (sockets), `e2e/tests/computer.spec.ts` (shared helpers in `karma-helpers.ts`).

## Conventions

- Server-authoritative: clients send intents only; validate with Zod, then with the game's `validateMove`.
- Live room/game state is in-memory; only users/stats are persisted in Postgres.
- Shared package is consumed as TS source (no build step). Use `import type` for types.
- Small focused commits, clear messages. Never commit `.env`.
- Keep this file updated as the project evolves.

## Opening animation (Home menu, `components/PogoStage.tsx`)

- The mascot is **Pogo the toad** (earlier drafts said frog; file and test names such as `sfx_frog_croak_single` and `animation/` keep the old word). Once per page load (module flag `introPlayed`, set when the toad lands **or by `markIntroSeen()` when the player leaves the menu on purpose** (entering a game room in `Shell`, opening Play or Join in `Home`): coming back with a back arrow / "Back to game selection" never replays it, even if he left mid-intro; a plain unmount does not count because the menu remounts briefly while connecting; with reduced motion it is skipped and the final state shows at once, which is why the e2e tests, which use reduced motion, never wait for it): the menu starts as an empty screen with only the pogo stick (`pogo-stage`) in the middle; the toad (side view) hops in from the left (`hop_in`, `mount` of `pogo-side-animation.json`), the landing switches to the front view and he bounces `AUTO_BOUNCES` (3) times, then rests (`pogo_extend`); from then on he only jumps when tapped (`pogo-jump` button over him: one `pogo_loop` cycle, one `pogoHit` sound). At the landing step `onLanded` flips `landed` in `Home`: the wordmark (`wordmark-die-o.svg`, POGO with a die as the last O, `home-wordmark`) pops in from scale 0 and then breathes +-5% (`.wordmark-in`, `index.css`), always tilted -10 degrees with clear space above the toad's head (no overlap); the whole group sits higher than centre (`pb-20`); the header slides in from the top and Play/Join + "Playing as" from the bottom (`.slide-top` / `.slide-bottom`, `data-in`). The **logo is placed exactly halfway between the bottom of the top bar (or the install banner when it shows) and the highest point the toad reaches** (`PEAK_ART` = 45 art px above the bottom of his stage: `pogo_air` at y -14, top row 1 of 32): Home measures the three boxes in a layout effect and absolutely positions the wordmark (`flat`: no clear space under it) at that midpoint plus 10px (`wordMid`, `LOGO_NUDGE`: the tilted corner clipped into the top bar). The toad is drawn 30% smaller than a whole-number scale (toad 4.375 / wordmark 11, or 3.5 / 8.8 scaled by `height / 700` under 700px height so Play and Join still fit; pixel art at a fractional scale is slightly uneven, that is accepted). While sound is blocked by the browser the stage shows "Tap to start" at the top of the stage, above the stick (`top-2` **inside** the stage: the stage root has `overflow-hidden`, so a label placed outside its box is clipped and invisible), and waits for the first tap. Headless Chromium starts with audio unlocked, so a test must suspend the `AudioContext` to see it.
- Timeline: all frames are stacked as `<img>`s with `visibility` toggled (no flicker while loading), steps come from the JSON (x/y art px relative to the stick, anchor bottom-centre, fx sprites with sizes in `FX_SIZE`). Sounds: `frogJump` on the first leap frame of each hop-in jump, `pogoHit` on every `pogo_compress` step (the landing too). Returning to the menu later shows him resting.

## Admin panel, roles, bans and the (dev) tag

- **Roles** (`packages/shared/src/protocol/roles.ts`): `PublicUser.role` = `user` (default, absent) | `moderator` | `admin`, plus the separate boolean `isDev`. `displayName(user)` = nickname + " (dev)" for developers; the server uses it for everything other players see (room member lists, game seats, chat, open-games host, leaderboard), while `PublicUser.nickname` stays plain (profile editing, tests). Staff need a registered account (they log in to the panel with email + password).
- **First admin**: env `ADMIN_EMAILS` (comma separated; `docker-compose.yml`, `.env.example`, `render.yaml`): at start-up, and whenever such an email registers or logs in, the account becomes admin (`withBootstrapRole` in `accountRoutes.ts`, loop in `app.ts`). After that, admins manage roles in the panel.
- **Developers**: env `DEV_EMAILS` (comma separated; compose, `.env.example`, `render.yaml`, local `.env`): these accounts become admin **and** `isDev` on every start-up and whenever they register or log in. The tag travels as the plain suffix `DEV_TAG` (" (dev)") in `displayName`; the web draws it as an animated rainbow "dev" through `PlayerName` (`components/PlayerName.tsx`, `splitDevTag`, CSS `.dev-tag`, still when reduced motion). Use `PlayerName` wherever a name is rendered as JSX; plain-text spots keep the literal suffix. The account must exist (register once), then set `DEV_EMAILS` in `.env` and restart.
- **Titles (prefix / suffix)**: a developer (`isDev`, not just admin) can give any **registered** player text before and after their nickname (paid perks or fun): `User.prefix` / `User.suffix` (Prisma migration `20261024000000_titles`), `PublicUser.prefix/suffix`, max `TITLE_MAX` (14) characters each, one line. `displayName` builds `prefix nickname suffix` plus the (dev) tag, so every place that already shows the display name (rooms, chat, leaderboard, seats) shows the titles after the player's next join/connect (rooms hold the user loaded at connect); the nickname itself stays editable by the player. API (dev only, 403 otherwise, logged in the audit log as `titles`): `POST /api/admin/users/:id/titles {prefix, suffix}` (empty = remove; guests refused). Web: `TitlesEditor` inside the player sheet of the **Players** tab (`AdminApp.tsx`, shown when `me.isDev` and the player is registered: live preview, tap-to-fill ideas, Save / Remove both). **Players tab**: registered players by default (`GET /api/admin/users?q=&registered=1`, up to 200 rows), chips Registered / Everyone / Guests, Online and Staff filters and a sort (last seen, newest, name), all client-side on top of the search box. **Settings shortcut**: developers see an "Admin panel" button (`settings-admin`) in the game's Settings; `openAdminPanel()` (`lib/session.ts`) copies the game token into `pogo.admin.token` and opens `/admin`, so there is no second login. **Account events in the Log tab** (`note()` in `accountRoutes.ts`, needs `moderation` in its deps): `register-requested`, `email-sent` / `email-failed` (with the MAIL code), `registered`, `login`, `login-failed`, `reset-requested`, `password-reset`; the address is masked (`ab***@host`). Test: `admin.test.ts` "titles (developers only)" and "account events in the log". After changing `schema.prisma` regenerate the client in the typecheck container: `docker compose run --rm --no-deps -w /app server sh -c "pnpm --filter @pogo/server prisma:generate; pnpm typecheck"` (a plain `make typecheck` uses a fresh volume with a stale client).
- **Powers**: moderator = search players, kick from a room, ban for up to 7 days (`MODERATOR_MAX_BAN_MINUTES`), lift bans, see rooms and the log; admin = also permanent bans, set roles (`POST /api/admin/users/:id/role`), give/remove the dev tag, see emails. Nobody can act on themselves or on someone of the same or higher rank (`target()` in `adminRoutes.ts`); guests cannot be given staff roles.
- **Server** (`apps/server/src`): `http/adminRoutes.ts` (`/api/admin/me|users|rooms|bans|audit`, `users/:id/kick|ban|role|dev`, `DELETE bans/:id`), `admin/moderation.ts` (`ModerationStore` Prisma/memory for `Ban` + `AuditLog`, `BanList` = in-memory index loaded at start so checks never hit the database, `banMessage`), `UserStore` additions (`search`, `setRole`, `setDev`, `touch`, `lastIpOf`; `User.lastIp/lastSeenAt` are updated on every socket connect), `RoomManager.evict/listAll/roomCodeOf`. Prisma migration `20261023000000_admin`.
- **Ban enforcement**: an `onRequest` hook in `app.ts` answers 403 `{banned: true, error}` to any `/api` call with a banned account's token; guest signup and login also refuse a banned IP (login: except staff, so an admin cannot lock themselves out); the socket handshake refuses a banned account or IP with `Error('banned')` (`data.message`), and banning disconnects the player's sockets and removes them from their room. A ban stores the IP the player last used when "block IP" is ticked (default). The web app shows the reason (`restoreSession` throws it; `useRealtime` returns `banned`, `Shell` renders a Banned screen and stops reconnecting).
- **Web** (`apps/web/src/admin`): `AdminApp.tsx` (login, tabs Players / Rooms / Bans / Log, a `Sheet` per player with kick, ban duration + reason + IP checkbox, role select and dev toggle), `adminApi.ts` (own token key `pogo.admin.token`). `main.tsx` renders it instead of the game when `isAdminSite()`: the hostname starts with `admin.` **or** the path starts with `/admin`, so `/admin` works on localhost and on the live address without any DNS.
- **Subdomain on Render**: add `admin.<your domain>` as a second custom domain of the same web service (Render dashboard, Settings, Custom Domains) and create the DNS CNAME it asks for; the single service serves both hosts (the SPA fallback returns the app for any path) and the panel appears because of the hostname. Cookies/localStorage are per origin, so you log in separately on the admin host.
- Tests: `apps/server/src/http/admin.test.ts`; `e2e/tests/admin.spec.ts` (runs only when the server has `ADMIN_EMAILS=admin-e2e@example.com`; it also needs `MAIL_MODE=log` because it registers through the dev mailbox, as `accounts.spec.ts` does: with `MAIL_MODE=smtp` in `.env` those e2e tests cannot read codes).
