# Pogo

Mobile-first multiplayer game hub (Plato-style): quick turn-based games with friends/strangers plus chat. First game: **Yatzy** (use "Yatzy" in the UI, never "Yahtzee"). Games are plug-ins; the core server/room/chat code must contain **no game-specific code**.

## Stack

TypeScript (strict) everywhere · pnpm workspaces · React 18 + Vite + Tailwind (PWA later) · Node 20 + Fastify + Socket.IO · PostgreSQL + Prisma · Zod for every inbound message/request · Vitest (unit) · Playwright (e2e, M4+) · ESLint + Prettier.

## Layout

```
apps/web        React/Vite client (dev server proxies /api and /socket.io to the server → one origin for phones)
apps/server     Fastify REST under /api + Socket.IO on the same HTTP server; Prisma in prisma/
packages/shared Types, Zod protocol schemas, GameDefinition interface, pure game logic (games/<id>)
docker/         Dev entrypoints   scripts/  Host helper scripts
```

Game plug-in split: pure logic in `packages/shared/src/games/<id>`, UI in `apps/web/src/games/<id>`, logic registry in `packages/shared/src/games/registry.ts` (`getGame(id)`), UI registry in `apps/web/src/games/registry.ts`. Rooms only see `GameDefinition` (createInitialState, validateMove, applyMove, getPlayerView, getCurrentPlayers, isGameOver, getResults, optional autoMove). Randomness is always an injected `Rng` (server: `crypto`; tests: `createSeededRng` / scripted `createDiceRng` from shared). `autoMove` is called repeatedly by the server until the timed-out player is no longer to move.

## Yatzy (packages/shared/src/games/yatzy)

Moves: `{type:'roll', held:boolean[5]}` (holds are sent with the roll; ignored on the first roll) and `{type:'score', category}`. Standard Joker rules: with Yatzy box filled, a further Yatzy forces the matching upper box, else any open lower box (full house/straights at full value), else any upper box for 0; +100 only if the Yatzy box holds 50. `getPreviewScores` drives the UI score preview.

## Realtime server (apps/server)

- `buildApp(deps)` in `src/app.ts` wires Fastify + Socket.IO + `RoomManager`; `index.ts` injects Prisma user store, crypto Rng and config (`loadConfig`). Tests inject an in-memory user store and seeded Rng.
- Identity: `POST /api/auth/guest {nickname, avatar}` → `{token, user}` (JWT, 90d; client keeps it in localStorage key `pogo.token`); `GET/PATCH /api/me`. Sockets authenticate with `auth: {token}` in the handshake.
- Rooms (`src/rooms`): `RoomManager` (code → `Room`, one room per user) and `Room` (members, settings, lifecycle, timers). They only use `GameDefinition`; tests use a fake game (`rooms/testGame.ts`) to prove it.
- Protocol (`packages/shared/src/protocol`): client emits `room:create|join|leave|kick|settings|start|rematch` and `game:move` with Zod-validated payloads and an ack `Result`; server pushes `room:state` (per-player filtered `RoomView`, or `null` + reason when you are no longer in a room) on every change and on (re)connect.
- Presence: a user is connected while ≥1 socket is open. Lobby: disconnected members are dropped after `DISCONNECT_GRACE_SEC`. In game: seat is kept; with a turn timer, if every current player is absent for the grace period (with unlimited time (`turnTimeSec` 0) nothing is ever auto-played for people who are merely disconnected; only players who left the room are still played for), or the turn timer (`TURN_TIME_SEC`, default 30 s; per-room `turnTimeSec`, 0 = off) runs out, the server auto-plays via `autoMove` (multi-step turns are paced ~1.2s apart). Rooms nobody is connected to are deleted after `ROOM_TTL_SEC`.
- Clock hooks on `GameDefinition` (all optional): `isFreeMove(move)` (a move that does not restart the turn clock), `keepsClock(before, after)` (the clock keeps running across the move: Karma's card swap has **one deadline for the whole phase**, started when the phase starts; no swap/Ready by anybody, computers included, resets it, and at the deadline everybody who is not ready is played by `autoMove` so the game starts), `clockBonusMs(state)` (extra time when the clock starts: Karma adds `rulesIntroMs(rules)` while the clients play the rules intro, so the swap time starts after the animation, during the tutorial). `Room.clockKept(before)` applies `keepsClock` in `move`, `autoplay` and `playBots`.
- Rate limiting: REST via `@fastify/rate-limit`; sockets via a per-socket token bucket (20 burst, 10/s).
- Share links look like `/?join=CODE` (handled by the web shell after sign-in).

## Error codes (troubleshooting)

- Every error shown to a player has a code behind the text: "Room not found (ROOM-101)". Unexpected server errors read "Something went wrong on our side (SYS-500 · ab12cd)": the 6-letter **ref** is also in the Render log line of that request (`ref`; for REST it is the request id, for sockets `newRef()`), so a screenshot is enough to find the cause. Anything not in the catalogue shows `SYS-000`.
- The catalogue is `packages/shared/src/protocol/errors.ts` (`KNOWN_ERRORS`: exact message or regex -> `AREA-NNN`; areas NET, SYS, MAIL, ACC, ADM, ROOM, GAME, YAT, KAR; 1xx = not allowed / the player's side, 5xx = ours). **To add an error: add its message to `KNOWN_ERRORS`**; `apps/server/src/errors.test.ts` scans the source for `error:`/`fail(`/`err(` string literals and fails for any message without a code. `failResult()` (used by `fail()` in `Room`/`RoomManager` and the socket handler) and a Fastify `preSerialization` hook in `app.ts` attach `code` to every socket ack and REST error body; the web shows `formatError(error, code, ref)` (`Shell` toasts, `lib/session.ts`, `admin/adminApi.ts`).
- Server errors: `app.setErrorHandler` answers anything thrown with `{error, code: 'SYS-500', ref}` and logs it with `code`/`ref` (the raw error never reaches the player); `AppError(status, code, message)` (`apps/server/src/errors.ts`) reports a chosen coded error. **Mail**: a failing send becomes a 502 with the friendly text "We couldn't send the email. Please try again in a minute." and a `MAIL` code from `mailFailure()`: MAIL-001 other/provider down, **MAIL-002 the provider refused our login or API key** (Brevo 401/403, SMTP EAUTH: check `BREVO_API_KEY`, it must be an API key `xkeysib-…`, not an SMTP key `xsmtpsib-…`), MAIL-003 the provider refused the mail (bad sender or address, Brevo 400), MAIL-004 unreachable/timeout (SMTP ports are blocked on Render's free tier), MAIL-006 provider rate limit, MAIL-005 dev mailbox empty. The log line carries the real cause in `cause`.

## Deployment (Render free tier + Neon, Frankfurt)

- `render.yaml` Blueprint → one Docker web service (`Dockerfile`, multi-stage: prod deps + Prisma client, web build, esbuild-bundled server). The server serves the built web app (`WEB_DIST_DIR`) with SPA fallback, so it is a single origin (no CORS/proxy). `docker/start.sh` runs `prisma migrate deploy` (retrying while Neon wakes), then `node dist/index.js`.
- Secrets are set in the Render dashboard (`sync: false`): `DATABASE_URL` (Neon, `?sslmode=require`; pooled hosts also need `&pgbouncer=true`) and optional `DIRECT_URL` (Neon direct string for migrations; defaults to `DATABASE_URL`). `JWT_SECRET` is generated by Render.
- Render health check is `/api/livez` (no DB access, so probes don't keep Neon awake); `/api/healthz` also checks the DB.
- Production runs with `trustProxy` so rate limits use the real client IP; only `/api` is rate limited.
- Free-tier caveats: spins down after 15 min without traffic (~1 min cold start); in-memory rooms are lost on restart/redeploy; single instance only.
- Test the prod image locally: `docker build -t pogo-prod .` then run it on the compose network with `DATABASE_URL` pointing at a scratch database.

## Public lobby & chat (M5)

- Rooms are `private` (default, join by code/link) or `public`. `Room.summary()` returns a `PublicRoomSummary` only for public rooms in `lobby` status that are not full; `RoomManager.listPublic()` sorts them longest-waiting first (cap 50). Clients call `lobby:subscribe` (joins the socket.io room `lobby`, ack = current list) and receive `lobby:list` pushes; `app.ts` debounces (150ms) and only pushes when the list actually changed. Subscriptions are lost on reconnect, so the web hook re-subscribes on `connect` (`watchLobby` in `lib/socket.ts`).
- `room:quickplay {gameId}` = join the longest-waiting open public room for that game (idempotent if you already wait in one), else create a public room.
- Chat is per room and in memory: `Room.chat()` sanitizes (`chatSendSchema`: one line, ≤300 chars), masks profanity (`maskProfanity` in `packages/shared/src/moderation`, a basic English+Dutch word list with leetspeak/boundary handling), keeps the last 100 messages and pushes `chat:message` to members; `chat:history` is sent on join/create/reconnect (it can arrive just before `room:state` on a refresh, which the web hook accounts for). Per-user flood limit in `socket/handlers.ts` (burst 5, then 1 per 2s) on top of the per-socket event limiter. Guest nicknames are also checked with `containsProfanity`. The whole filter is switched by the server setting `PROFANITY_FILTER=on|off` (default on; `maskText` is injected into the rooms, nickname refusal is in `authRoutes`). It is currently **off** in `render.yaml` (flip it in the Render dashboard under Environment) and in the local `.env`; the e2e tests read the same variable so they pass either way.
- Chat message layout (`ChatPanel`): a square icon tile (`Avatar size="chat"`, as high as the name line plus a one-line bubble: its bottom edge lines up with the bubble) on the outer edge of each message (left for others, right for mine), the bold name above the bubble (the pixel font has no bold weight, so `font-bold` is thickened with a 1px `text-shadow`).
- Web: `ChatPanel` (inline in the lobby, in a bottom `Sheet` during games with an unread badge on the header chat button), open games list on `Home`.

## Karma (the "Shithead" card game; packages/shared/src/games/karma, apps/web/src/games/karma)

- Implements the base rules from https://en.wikipedia.org/wiki/Shithead_(card_game): 2-5 players, one 52-card deck, 3 face-down + 3 face-up + 3 hand cards each, rest is the draw deck. Cards are numbers 0-51 (`suit = floor(c/13)`, `rank = c%13+2`, J=11..A=14).
- Phases: `swap` (everyone acts at once: swap a hand card with a face-up slot, then `ready`; hidden until all ready) → `play` → `over`. The starter holds the lowest ordinary card (4 up to ace; 2, 3 and 10 are specials and never start) among face-up cards and hands; equal ranks are decided by suit: clubs, diamonds, hearts, spades; only specials around = first seat (`findStarter`).
- Turn: play one card or a set of the same rank, equal or higher than the top card, from hand first, then face-up, then face-down (blind, one at a time); or `pickup` the whole pile (allowed even if a play exists). 2 plays on anything and anything plays on a 2. An **8 skips the next player** (`advance(..., skips)` in `game.ts`): each 8 in the played set skips one more active player, you can never skip yourself so with two players an 8 simply means you go again, a burn (10 / four of a kind) takes priority over skipping, a blind 8 skips too, a failed blind card never does, and the skipped ids are in `KarmaEvent.skipped` for the UI. After a 7 the next card must be **7 or lower** (3-7, so 7s stack on 7s), a 2 or a 10 (a "lower or equal" house variant; `canPlayRank` is the single source of truth, also used by the UI to dim cards). 10 plays at any time on anything (including after a 7) and burns the pile; four of a kind on top of the pile burns it too (played at once or completed over turns). After a burn the same player leads again. After every play the hand is refilled to 3 from the deck. A face-up card may always be tried: when too low it goes onto the pile like a failed blind card (`failed`, `mustPickUp`, then `pickup` takes the pile including it); hand cards must still be playable. A too-low blind card is turned over and lies on the pile (event `failed: true`, state/view `mustPickUp`): its owner's only move is then `pickup` (a separate move and event, so everyone sees the card first); `autoMove` and bots do it by themselves.
- Decisions where the article is silent: jokers are not used; **a 3 is invisible** (house rule, `effectiveTop` in `game.ts`: a 3 is always playable and the next play is measured against the topmost non-3 card, so 7, 3 still means "7 or lower"; a pile of only 3s counts as empty; the four-of-a-kind burn still looks at the physical top four cards). Other variants are not implemented (7 = "lower or equal" and 8 = "skip" are); a player who burns with their last card is out and play passes on; ranks are by the order players ran out, the last player left is the loser (`score = players - rank`).
- End of game (leftovers): when the game is over (`phase` `'over'`) `KarmaView.leftovers` carries what the player who is left still holds (hand + the real face-down cards; `null` earlier, so nothing leaks). The table is **not** cleared when the game ends (my dock stays; moves are impossible anyway) and the loser's cards turn over in place: face-down cards first, then the hand, on their seat (`Seat`/`TableSlots.revealDown`/`HandFan.faces`) or in my own dock when I am the loser, each a `FlipReveal` (back shrinks away, face grows in: `card-back-out`/`card-face-in` in `index.css`, instant with reduced motion). Timing is in `games/karma/reveal.ts`: the turning **starts when the game is really over**: after a last face-down card (which has its own win reveal) when that card has finished turning, i.e. when the confetti starts (`AFTER_LAST_CARD_MS` = `TURN_MS` + a beat; keep the two in step), otherwise 0.7 s after the last move; one card per `revealStep` (420 ms, quicker for a huge hand), each turn takes `REVEAL_FLIP_MS` (700 ms); `resultsDelayMs` holds the standings back until it is all done plus `REVEAL_HOLD_MS` (1.5 s).
- Privacy: `getPlayerView` gives each player only their own hand; face-down cards are hidden from everyone including their owner (the view only says which slots still hold a card); the deck is a count. The pile and face-up cards are public. `lastEvent` (seq, kind, cards, burned, pickedUp, out) narrates the latest move to every client.
- `autoMove`: swap = ready; otherwise lowest legal rank (specials 2/10 last, whole set of that rank; 1 time in 4 the second-lowest, see below), else pick up; blind = first remaining slot. It reports `endsTurn` by simulating the move, so a burn (same player again) is paced like Yatzy's multi-step turns.
- **Games can loop forever under deterministic play.** With the 7 rule (and 8 skips) a fixed "always play the lowest card" strategy can circle indefinitely, e.g. a 7 that nobody can follow is picked up and led again. Measured over 500 games per size: ~1 in 500 stuck for always-lowest sets, 4-6% for single-card plays, **0 in 2000 once there is a 25% chance of the second-lowest rank** (that is what `autoMove` and the e2e strategy do; `game.test.ts` runs 600 auto-played games to guard it). Any bot or test strategy for Karma must include randomness and play sets. Humans do not loop in practice; the room's absent-player auto-play and abandoned-room TTL bound the damage anyway.
- Card animation (FLIP, in `PlayingCard.tsx`): every card with a `flip={{id, origin?}}` prop records its on-screen box after each render (module-level `lastBoxes`, keyed by card id, cleared on resize); if a card's box changed (hand re-fan, swap between hand and face-up slot, hand -> pile) it slides from the old box with the Web Animations API (320ms). A card never seen before (drawn from the deck, picked up from the pile, an opponent's hand card landing on the pile) starts from an `origin` anchor (deck / pile / that opponent's seat). The outer element is what moves, and a card's remembered box is its _layout_ box (the running animation's transform is subtracted, otherwise re-renders mid-flight start bogus slides); deck/pile origins are points so cards grow out of them at their own proportions. The action column is the timer (2 parts) over the Play button (3 parts) filling everything to the right of my table cards, which sit at the left (the column is always shown; Play is only disabled off-turn, so the layout never bumps between turns). There is no Pick up button and no automatic pickup: when nothing in the active zone can be played (`mustPickUp`) the pile pulses (`.pile-pulse`) and ONE tap picks it up (a voluntary pickup is two taps). The cards of a multi-card play leave one after another (170ms apart, 520ms flights; `playFlight`, `delayMoves`) so you can see how many were thrown. The picked-up cards then fly from the pile into the hand one by one (`delay` in `FlipProps`, ~700ms total). Burns resolve instantly on the server, so the client keeps the played cards visible on the pile for `GHOST_MS` (1.1s; a four-of-a-kind burn instead plays the `FourBurn` overlay for `FOUR_BURN_MS`: table dimmed, four cards side by side, fire, fade; its fire carries `burn-flash`, `ghost` state; flame and fling wait for it); selection lift and pile tilt live on an inner element so they never count as movement. Animations are off for the first paint and when `prefers-reduced-motion` is set (`CardFlipContext`); **tests that tap cards must use reduced motion**, otherwise Playwright waits for each sliding card to settle.

## Karma game modes and rules

- **Endgame table cards**: when my hand and the deck are empty (`endgame` in `KarmaGame`) my table cards leave the top-left slot and are drawn in the hand row instead (`TableSlots spread`: only columns that still hold a card, centred, so two recentre; `egFont` fills the width), the timer + Play fill the whole top row, and when cards come back into my hand they slide back up. The slide is the normal FLIP: face-up cards have their card id, my face-down cards a stand-in id (`-1 - slot`).
- **Mode picker (`ModePicker`)**: choosing a mode shows no bubble; tapping the chosen mode again shows (and hides) it. Party and Epic list **every** rule as a chip (`karma-rule-<id>`, `data-active`): the ones that are on are normal, the ones that are off are greyed out, each chip ends with a green tick (on) or a red cross (off) at full colour (`karma-rule-mark-<id>`, `data-on`), and every chip still opens its description bubble.

- Room option `{mode: 'normal'|'party'|'epic', rules: string[]}` (`KarmaOptions`, default normal; the host picks the mode in the lobby through the generic `GameUi.LobbyOptions` slot, `ModePicker`, test ids `karma-mode-<mode>`, `karma-active-rules`; nothing is explained by default: tapping a mode or a rule chip (emoji + name, `karma-rule-<id>`) floats a small `info-bubble` over the UI under it (centred with a negative margin, **not** `-translate-x-1/2`: the slide-in animation sets `transform` and would cancel a translate, shoving the bubble under the next button; the e2e suite runs with reduced motion, which switches that animation off, so such bugs only show with motion on), `karma-mode-bubble` / `karma-rule-bubble`, fading in with a small slide; it closes on a second tap or a tap elsewhere). The catalogue is `KARMA_RULES` in `packages/shared/src/games/karma/rules.ts` (id, name, emoji, description); **adding a rule = one catalogue entry + its effect in `game.ts`** (search for `hasRule`). The extra rules are `bigHand` (four cards in hand) and `echoThree` ("3 ate 8" 3️⃣: a 3 repeats the 8 beneath it, so it skips the next player again, once per 3 played; `playToPile` looks through other 3s via `effectiveTop`, and the 7/2/10 already carry through a 3 without the rule). **`fastReload`** ("Fast reload" ⚡): after you play cards from your hand and refill from the deck, if a **drawn** card has the rank you just played (not after a burn, which lets you lead freely anyway) you may play it too before the turn passes. State `reload = {rank, skips}` (`skips` = 8s played so far this turn: they still skip when the turn finally passes, also across a chain of reloads), the player stays `state.turn`; validation allows only `play` of that rank from the hand or the new move `{type:'skipReload'}` (which runs `advance` with the pending skips); `KarmaView.reload = {rank}`; `autoMove` plays the matching cards (so computers use the rule) else skips. UI (`KarmaGame`): only cards of that rank can be selected (the rest are dimmed, `tapCard` ignores them, the pile is not a pick-up), the hint says "⚡ Fast reload: play the matching card, or press Skip", and the Play button reads **Skip** (`karma-play`, sends `skipReload`) until a matching card is selected, then it is the normal Play button. **`jokers`** ("Joker returns" 🃏): two jokers (card ids 52 and 53, `isJoker`, `rankOf` = `JOKER_RANK` 15; `shuffledDeck(rng, true)` builds the 54-card deck, the move schema allows ids up to 53) join the deck. A joker can always be played (`canPlayRank`), is invisible like a 3 (`effectiveTop` skips it, a pile of only jokers counts as empty), never burns, never triggers a fast reload, and **turns the direction of play around**: `KarmaState.direction` (`1` = clockwise = up the seat order, `-1` = counter clockwise; `nextActive` and 8-skips follow it; `view.direction`); an odd number of jokers in one play flips it (two at once cancel), and when only two players are left it simply means you **play again** (like an 8, `advance(..., jokers)`). `autoMove` plays jokers last. UI: the joker art (`cardFaceUrl`), a direction arrow after the pile count (`karma-direction`, `data-direction`, ↻/↺, only when the rule is on), and the event line adds "direction reversed ↺". The earlier jacksSkip, tripleBurn, aceBurn and sixesWild were removed. `state.rules` / `view.rules` are the rules in force.
- normal: no rules. epic: all rules from the first game, every game. party: **round 1 starts without rules; from round 2 on the winner of the previous game sets the rules before the cards are dealt.** `KarmaOptions` carries `round` (1 = first game of the room, `nextOptions` adds one per game), `rules` (the party rules as set) and `pickerId` (the last winner, `finishOrder[0]`); `Room.rematch` calls `GameDefinition.nextOptions(state, options)` when the room goes back to the lobby (there is no instant restart any more: `restartOnRematch` is not used by Karma; changing the mode in the lobby resets round/rules because the options are replaced). `createInitialState` for party with `round > 1` starts in phase **`pick`** with nothing dealt (`state.pick = {playerId, choices}`, the picker falls back to the first seat when the last winner left; `getCurrentPlayers` = the picker, so the turn clock runs): the picker plays `{type:'toggleRule', rule}` (switches one rule on or off; a **free move**, `isFreeMove`, so it does not restart the clock; everybody sees `view.rules` change live) and `{type:'confirmRules'}`, which deals the cards for the rules then in force (big hand changes the hand size, hence the late deal) and starts the swap phase. `autoMove` (computer picker, absent player, timeout) confirms the rules unchanged. `KarmaView.round` and `view.pick` drive the UI. The old end-of-game pick (`pickRule`, `nextRules`, `GameUi.pendingResults`/`ResultsExtra`, `RulePick`) is gone: the results screen only has the standings, the register nudge and Lobby/Exit.
- UI, **round screen** (`RoundScreen.tsx`, `round-screen` with `data-mine`; rendered by `KarmaGame` while `view.phase === 'pick'`, a full-screen overlay): the title "Round N" pops in (`round-pop`), the line says who won the last game and sets the rules, then every rule from the catalogue as a row (`round-rule-<id>`, `data-active`: emoji, name, what it does, a tick box: green tick = on, red cross = off; the rows slide in from the left, `round-row`). The picker taps rows to switch them (each tap is a `toggleRule`), everybody else sees the same rows change live (disabled buttons), and the big `round-confirm` button (`confirmRules`) carries the turn clock as a draining `TimerDrain` bar like the other buttons; for the others it reads "Waiting for <name>…" with the same bar. With reduced motion the animations are off but the screen still works (it is functional, not decoration).
- **Rules intro** (`RulesIntro.tsx`, `rules-intro`, `data-stage`): when a game starts with rules in force (party after the round screen, or epic) and before anything else moves (card swap, tutorial) the game sits dimmed (`bg-black/70`) while the banner "🎉 Party rules:" (epic: "🔥 Epic rules:") flies in from the top, the active rules fly in from the left one after another (emoji, name, description), hold (~1.4 s + 0.9 s per rule), then the banner leaves upwards, the rules fly out to the right and the overlay fades so the brightness returns; a tap skips it; the tutorial opens after it. Not shown with no rules (empty = skipped), in normal mode, or with reduced motion (the e2e suite). `KarmaGame` decides in `intro` / `tutorial` state and on the `pick` → `swap` transition.

## Computer players (bots)

- A game opts in with `GameDefinition.supportsBots` (Karma only; Yatzy's `autoMove` is too basic and it has a solo mode anyway). Bots are ordinary seats in the game state: ids `bot:1..n`, names from `BOT_NAMES` (skipping names people in the room use), avatar `robot` (`packages/shared/src/game/bots.ts`). They are **not** room members for auth/chat/kick/capacity purposes (`Room.hasMember`, `memberCount`, `activeMemberIds` exclude them) but appear in `RoomView.members` with `bot: true` so the UI can name them.
- Room setting `bots` (create, `room:settings`, `RoomView.bots`). Seats are added in `Room.start()` after the people and removed on rematch (the setting stays). `room:create {gameId, bots, autoStart: true}` is the one-tap "Play the computer" flow (private room, starts at once). Total seats must fit `game.maxPlayers`; joining people count against `memberCount + bots`.
- Driving them: `Room.botDue()` / `playBots()` wake the room `botMs` after the last state change (env `BOT_DELAY_MS`, 700 in dev compose, 1000 default) and every bot that is up makes one `autoMove`. They pause while no person is connected, a room with no people closes immediately (`afterMembershipChange`) or after the TTL, and no clock is shown (`deadline: null`) while only bots are up. Bots never see anyone's private cards: they use the full server state like `autoMove` for absent players, and clients still only receive `getPlayerView`.
- Quality: Karma's `autoMove` swaps strong cards (10, 2, aces, kings...) face-up with `bestSwap` (a swap must gain >= 2 `tableValue`), then plays lowest-rank-first with a 25% second-lowest jitter. It is deliberately easy-ish; there is no difficulty setting yet.
- Web: the lobby has a "Computer players" stepper and a "Start vs computer" button; Karma seats of bots show "CPU ·". Tests: `RoomManager.test.ts` (fake timers, a whole game vs 2 bots), `app.test.ts` (sockets), `e2e/tests/computer.spec.ts` (shared helpers in `karma-helpers.ts`).

## End-to-end tests (e2e/)

Standalone Playwright project (own `package.json`/lockfile, not part of the pnpm workspace) running in the official Playwright image against the compose stack: `make e2e` (= `docker compose --profile e2e run --rm e2e`, needs the stack up). It plays a full two-player Yatzy game with a mid-turn reload, plus a share-link join and kick test. Playwright version in `e2e/package.json`, `e2e/Dockerfile` must match.

## Conventions

- Server-authoritative: clients send intents only; validate with Zod, then with the game's `validateMove`.
- Live room/game state is in-memory; only users/stats are persisted in Postgres.
- Shared package is consumed as TS source (no build step). Use `import type` for types.
- Small focused commits, clear messages. Never commit `.env`.
- Keep this file updated as the project evolves.

## Running (everything runs in Docker; host needs only Docker + make)

- `make up` – build + start detached (creates `.env` from `.env.example`, detects LAN IPs) and prints URLs
- `make down` / `make logs` / `make ps` / `make urls`
- `make test` · `make lint` · `make typecheck` · `make format`
- `make migrate` · `make db-reset` (destructive) · `make db-shell` · `make shell`

## Chat banner, reveal spoilers and new games (Karma)

- `ChatBanner` (`components/ChatBanner.tsx`, mounted in `Shell`, `data-testid="chat-banner"`): a chat message from somebody else slides down from the top like a notification, as high as the header (`3.5rem` + safe area), one line cut off with `…` (`truncate`), 3.6s (`chat-banner` keyframes in `index.css`, off with reduced motion), tap to dismiss. History loaded on joining is not announced (only appended messages, or the first message of a fresh room).
- While a card turns over (`reveal`, or the render before it is set: `revealPending`) `KarmaGame` shows **no turn information**: `myTurnShown`/`shownTurnId` keep the flipper as the current player, so the hand is dimmed, nothing is highlighted as playable and the turn ping waits; otherwise you could tell from your own turn whether the flip was too low (the flipper keeps the turn and must pick up) or fine.
- The result sound of a last card and the winner's fanfare play when the card has finished turning (`TURN_MS`, `GameUi.ownFanfare`: `GameScreen` then stays silent; other games play it when the standings appear).
- `GameScreen` mounts the game component with a key that changes every time the room goes to `playing` again, and `KarmaGame` clears the card position cache (`resetFlipBoxes`), so an instant rematch starts from a clean UI (state of the previous game, such as old selections or card positions, used to leak into the new one).
- The robot icon is reserved for computer players (`BOT_AVATAR`; not in `AVATARS`, so nobody can pick it; accounts that had it get the fox in `toPublic`). Avatars are **square tiles** (`Avatar` in `components/ui.tsx`, `rounded-[6px]` with the dark outline). On Home, tapping your own icon (`home-avatar`) opens a `Sheet` with square tiles (`pick-avatar-<id>`); picking one saves it with `PATCH /api/me` (`updateProfile` in `lib/session.ts`, `App` keeps the user in state through `Shell`'s `onUser`). It only changes on Home: a room keeps the icon the player joined with.
- **Menu boxes are gold-orange** (`.menu` on the Home and Lobby roots and on every `Sheet` dialog): inside a `.menu .hud` the tokens are re-pointed (`panel` `#fda200`, `panel2` `#ea9600`, `ink` navy, `muted` brown, `neon` navy, `accent` deeper blue with white text, `dangertext` dark red), so no component needs to know; things on the table outside a box and the game tables (Yatzy dock and scorecard, Karma, results) keep the blue-slate panels.
- **Cards are the artist's pixel-art SVGs** (`assets/sprites/cards/`, 45x61 art px; `games/karma/cardArt.ts` maps a card number to its file: suit index 0-3 = S,H,D,C, rank 2-14 = 2..10,J,Q,K,A; `back.svg` is the back). `PlayingCard` draws an `<img>` stretched to its 5em x 7em box (3% off the art ratio, invisible) and applies dimming, the selection outline (gold drop-shadows) and the lift shadow as CSS `filter`s, because the art has its own rounded outline. The old code-drawn faces and `PixelSuit` are gone: to redesign a suit or a card, replace the SVG (see the assets section).

## Opening animation (Home menu, `components/PogoStage.tsx`)

- The mascot is **Pogo the toad** (earlier drafts said frog; file and test names such as `sfx_frog_croak_single` and `animation/` keep the old word). Once per page load (module flag `introPlayed`, set when the toad lands **or by `markIntroSeen()` when the player leaves the menu on purpose** (entering a game room in `Shell`, opening Play or Join in `Home`): coming back with a back arrow / "Back to game selection" never replays it, even if he left mid-intro; a plain unmount does not count because the menu remounts briefly while connecting; with reduced motion it is skipped and the final state shows at once, which is why the e2e tests, which use reduced motion, never wait for it): the menu starts as an empty screen with only the pogo stick (`pogo-stage`) in the middle; the toad (side view) hops in from the left (`hop_in`, `mount` of `pogo-side-animation.json`), the landing switches to the front view and he bounces `AUTO_BOUNCES` (3) times, then rests (`pogo_extend`); from then on he only jumps when tapped (`pogo-jump` button over him: one `pogo_loop` cycle, one `pogoHit` sound). At the landing step `onLanded` flips `landed` in `Home`: the wordmark (`wordmark-die-o.svg`, POGO with a die as the last O, `home-wordmark`) pops in from scale 0 and then breathes +-5% (`.wordmark-in`, `index.css`), always tilted -10 degrees with clear space above the toad's head (no overlap); the whole group sits higher than centre (`pb-20`); the header slides in from the top and Play/Join + "Playing as" from the bottom (`.slide-top` / `.slide-bottom`, `data-in`). The toad is drawn 30% smaller than a whole-number scale (toad 4.375 / wordmark 11, or 3.5 / 8.8 scaled by `height / 700` under 700px height so Play and Join still fit; pixel art at a fractional scale is slightly uneven, that is accepted). While sound is blocked by the browser the stage shows "Tap to start" at the top of the stage, above the stick (`top-2` **inside** the stage: the stage root has `overflow-hidden`, so a label placed outside its box is clipped and invisible), and waits for the first tap. Headless Chromium starts with audio unlocked, so a test must suspend the `AudioContext` to see it.
- Timeline: all frames are stacked as `<img>`s with `visibility` toggled (no flicker while loading), steps come from the JSON (x/y art px relative to the stick, anchor bottom-centre, fx sprites with sizes in `FX_SIZE`). Sounds: `frogJump` on the first leap frame of each hop-in jump, `pogoHit` on every `pogo_compress` step (the landing too). Returning to the menu later shows him resting.
- `e2e/tests/intro.spec.ts` plays the real animation (motion enabled) and writes screenshots to `e2e/test-results/`.

## Admin panel, roles, bans and the (dev) tag

- **Roles** (`packages/shared/src/protocol/roles.ts`): `PublicUser.role` = `user` (default, absent) | `moderator` | `admin`, plus the separate boolean `isDev`. `displayName(user)` = nickname + " (dev)" for developers; the server uses it for everything other players see (room member lists, game seats, chat, open-games host, leaderboard), while `PublicUser.nickname` stays plain (profile editing, tests). Staff need a registered account (they log in to the panel with email + password).
- **First admin**: env `ADMIN_EMAILS` (comma separated; `docker-compose.yml`, `.env.example`, `render.yaml`): at start-up, and whenever such an email registers or logs in, the account becomes admin (`withBootstrapRole` in `accountRoutes.ts`, loop in `app.ts`). After that, admins manage roles in the panel.
- **Powers**: moderator = search players, kick from a room, ban for up to 7 days (`MODERATOR_MAX_BAN_MINUTES`), lift bans, see rooms and the log; admin = also permanent bans, set roles (`POST /api/admin/users/:id/role`), give/remove the dev tag, see emails. Nobody can act on themselves or on someone of the same or higher rank (`target()` in `adminRoutes.ts`); guests cannot be given staff roles.
- **Server** (`apps/server/src`): `http/adminRoutes.ts` (`/api/admin/me|users|rooms|bans|audit`, `users/:id/kick|ban|role|dev`, `DELETE bans/:id`), `admin/moderation.ts` (`ModerationStore` Prisma/memory for `Ban` + `AuditLog`, `BanList` = in-memory index loaded at start so checks never hit the database, `banMessage`), `UserStore` additions (`search`, `setRole`, `setDev`, `touch`, `lastIpOf`; `User.lastIp/lastSeenAt` are updated on every socket connect), `RoomManager.evict/listAll/roomCodeOf`. Prisma migration `20261023000000_admin`.
- **Ban enforcement**: an `onRequest` hook in `app.ts` answers 403 `{banned: true, error}` to any `/api` call with a banned account's token; guest signup and login also refuse a banned IP (login: except staff, so an admin cannot lock themselves out); the socket handshake refuses a banned account or IP with `Error('banned')` (`data.message`), and banning disconnects the player's sockets and removes them from their room. A ban stores the IP the player last used when "block IP" is ticked (default). The web app shows the reason (`restoreSession` throws it; `useRealtime` returns `banned`, `Shell` renders a Banned screen and stops reconnecting).
- **Web** (`apps/web/src/admin`): `AdminApp.tsx` (login, tabs Players / Rooms / Bans / Log, a `Sheet` per player with kick, ban duration + reason + IP checkbox, role select and dev toggle), `adminApi.ts` (own token key `pogo.admin.token`). `main.tsx` renders it instead of the game when `isAdminSite()`: the hostname starts with `admin.` **or** the path starts with `/admin`, so `/admin` works on localhost and on the live address without any DNS.
- **Subdomain on Render**: add `admin.<your domain>` as a second custom domain of the same web service (Render dashboard, Settings, Custom Domains) and create the DNS CNAME it asks for; the single service serves both hosts (the SPA fallback returns the app for any path) and the panel appears because of the hostname. Cookies/localStorage are per origin, so you log in separately on the admin host.
- Tests: `apps/server/src/http/admin.test.ts`; `e2e/tests/admin.spec.ts` (runs only when the server has `ADMIN_EMAILS=admin-e2e@example.com`; it also needs `MAIL_MODE=log` because it registers through the dev mailbox, as `accounts.spec.ts` does: with `MAIL_MODE=smtp` in `.env` those e2e tests cannot read codes).
