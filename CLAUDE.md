# Pogo

Mobile-first multiplayer game hub (Plato-style): quick turn-based games with friends/strangers plus chat. First game: **Yatzy** (use "Yatzy" in the UI, never "Yahtzee"). Games are plug-ins; the core server/room/chat code must contain **no game-specific code**.

## Stack

TypeScript (strict) everywhere · pnpm workspaces · React 18 + Vite + Tailwind (PWA later) · Node 20 + Fastify + Socket.IO · PostgreSQL + Prisma · Zod for every inbound message/request · Vitest (unit) · Playwright (e2e, M4+) · ESLint + Prettier.

## Layout

```
apps/web        React/Vite client (dev server proxies /api and /socket.io to the server → one origin for phones)
apps/server     Fastify REST under /api + Socket.IO on the same HTTP server; Prisma in prisma/
packages/shared Types, Zod protocol schemas, GameDefinition interface, pure game logic (games/<id>)
docker/         Dev entrypoints   scripts/  Host helper scripts
```

Game plug-in split: pure logic in `packages/shared/src/games/<id>`, UI in `apps/web/src/games/<id>`, logic registry in `packages/shared/src/games/registry.ts` (`getGame(id)`), UI registry in `apps/web/src/games/registry.ts`. Rooms only see `GameDefinition` (createInitialState, validateMove, applyMove, getPlayerView, getCurrentPlayers, isGameOver, getResults, optional autoMove). Randomness is always an injected `Rng` (server: `crypto`; tests: `createSeededRng` / scripted `createDiceRng` from shared). `autoMove` is called repeatedly by the server until the timed-out player is no longer to move.

## Yatzy (packages/shared/src/games/yatzy)

Moves: `{type:'roll', held:boolean[5]}` (holds are sent with the roll; ignored on the first roll) and `{type:'score', category}`. Standard Joker rules: with Yatzy box filled, a further Yatzy forces the matching upper box, else any open lower box (full house/straights at full value), else any upper box for 0; +100 only if the Yatzy box holds 50. `getPreviewScores` drives the UI score preview.

## Realtime server (apps/server)

- `buildApp(deps)` in `src/app.ts` wires Fastify + Socket.IO + `RoomManager`; `index.ts` injects Prisma user store, crypto Rng and config (`loadConfig`). Tests inject an in-memory user store and seeded Rng.
- Identity: `POST /api/auth/guest {nickname, avatar}` → `{token, user}` (JWT, 90d; client keeps it in localStorage key `pogo.token`); `GET/PATCH /api/me`. Sockets authenticate with `auth: {token}` in the handshake.
- Rooms (`src/rooms`): `RoomManager` (code → `Room`, one room per user) and `Room` (members, settings, lifecycle, timers). They only use `GameDefinition`; tests use a fake game (`rooms/testGame.ts`) to prove it.
- Protocol (`packages/shared/src/protocol`): client emits `room:create|join|leave|kick|settings|start|rematch` and `game:move` with Zod-validated payloads and an ack `Result`; server pushes `room:state` (per-player filtered `RoomView`, or `null` + reason when you are no longer in a room) on every change and on (re)connect.
- Presence: a user is connected while ≥1 socket is open. Lobby: disconnected members are dropped after `DISCONNECT_GRACE_SEC`. In game: seat is kept; if every current player is absent for the grace period, or the turn timer (`TURN_TIME_SEC`, per-room `turnTimeSec`, 0 = off) runs out, the server auto-plays via `autoMove` (multi-step turns are paced ~1.2s apart). Rooms nobody is connected to are deleted after `ROOM_TTL_SEC`.
- Rate limiting: REST via `@fastify/rate-limit`; sockets via a per-socket token bucket (20 burst, 10/s).
- Share links look like `/?join=CODE` (handled by the web shell after sign-in).

## Deployment (Render free tier + Neon, Frankfurt)

- `render.yaml` Blueprint → one Docker web service (`Dockerfile`, multi-stage: prod deps + Prisma client, web build, esbuild-bundled server). The server serves the built web app (`WEB_DIST_DIR`) with SPA fallback, so it is a single origin (no CORS/proxy). `docker/start.sh` runs `prisma migrate deploy` (retrying while Neon wakes), then `node dist/index.js`.
- Secrets are set in the Render dashboard (`sync: false`): `DATABASE_URL` (Neon, `?sslmode=require`; pooled hosts also need `&pgbouncer=true`) and optional `DIRECT_URL` (Neon direct string for migrations; defaults to `DATABASE_URL`). `JWT_SECRET` is generated by Render.
- Render health check is `/api/livez` (no DB access, so probes don't keep Neon awake); `/api/healthz` also checks the DB.
- Production runs with `trustProxy` so rate limits use the real client IP; only `/api` is rate limited.
- Free-tier caveats: spins down after 15 min without traffic (~1 min cold start); in-memory rooms are lost on restart/redeploy; single instance only.
- Test the prod image locally: `docker build -t pogo-prod .` then run it on the compose network with `DATABASE_URL` pointing at a scratch database.

## Public lobby & chat (M5)

- Rooms are `private` (default, join by code/link) or `public`. `Room.summary()` returns a `PublicRoomSummary` only for public rooms in `lobby` status that are not full; `RoomManager.listPublic()` sorts them longest-waiting first (cap 50). Clients call `lobby:subscribe` (joins the socket.io room `lobby`, ack = current list) and receive `lobby:list` pushes; `app.ts` debounces (150ms) and only pushes when the list actually changed. Subscriptions are lost on reconnect, so the web hook re-subscribes on `connect` (`watchLobby` in `lib/socket.ts`).
- `room:quickplay {gameId}` = join the longest-waiting open public room for that game (idempotent if you already wait in one), else create a public room.
- Chat is per room and in memory: `Room.chat()` sanitizes (`chatSendSchema`: one line, ≤300 chars), masks profanity (`maskProfanity` in `packages/shared/src/moderation`, a basic English+Dutch word list with leetspeak/boundary handling), keeps the last 100 messages and pushes `chat:message` to members; `chat:history` is sent on join/create/reconnect (it can arrive just before `room:state` on a refresh, which the web hook accounts for). Per-user flood limit in `socket/handlers.ts` (burst 5, then 1 per 2s) on top of the per-socket event limiter. Guest nicknames are also checked with `containsProfanity`. The whole filter is switched by the server setting `PROFANITY_FILTER=on|off` (default on; `maskText` is injected into the rooms, nickname refusal is in `authRoutes`). It is currently **off** in `render.yaml` (flip it in the Render dashboard under Environment) and in the local `.env`; the e2e tests read the same variable so they pass either way.
- Web: `ChatPanel` (inline in the waiting room, in a bottom `Sheet` during games with an unread badge on the header chat button), open games list + Quick match on `Home`.

## Web app (apps/web)

- Screens are driven by the server's `room:state`: `Shell.tsx` owns the socket (`lib/socket.ts`) and renders `Home` (no room), `Lobby` (status `lobby`) or `GameScreen` (`playing`/`finished`, includes the generic results panel). Screens call the server only through the `RoomApi` object (`lib/api.ts`), and failures are toasted centrally in the shell.
- Game UI plug-in: add a `GameUi` (`games/types.ts`: id, name, emoji, tagline, `Component({room, me, sendMove})`) and register it in `games/registry.ts`. Yatzy lives in `games/yatzy/` (`YatzyGame` = turn banner + `Scorecard` + dice dock with `Die`).
- Yatzy UX: holds are local until you roll; tap a category chip then "Score"; the roll animation is cosmetic (faces flicker with `Math.random`, real values come from the server). `prefers-reduced-motion` skips animations (the e2e tests rely on this).
- Settings (sound, vibration, theme auto/light/dark) are in `lib/settings.ts` (localStorage `pogo.settings`); sounds are synthesized with WebAudio (`lib/sound.ts`, no audio files); haptics use `navigator.vibrate` (`lib/haptics.ts`).
- Yatzy layout rule: the whole scorecard + dice + buttons must fit one screen without vertical scrolling at 390x700 (enforced by an e2e test). `YatzyGame` measures the free space (ResizeObserver) and passes `fillHeight` so the table's rows stretch to use it; row/chip heights are deliberately tight (24px) and there is a denser variant under `max-height: 640px`. Horizontal scroll (many players) is fine. Avoid inline content in table cells (line boxes add height): keep cells `h-6 leading-none` and chips `block`.
- Stable `data-testid`s (e.g. `roll-button`, `pick-<category>`, `score-button`, `turn-banner`, `results-panel`) are used by the e2e tests; keep them when refactoring.

## Karma (the "Shithead" card game; packages/shared/src/games/karma, apps/web/src/games/karma)

- Implements the base rules from https://en.wikipedia.org/wiki/Shithead_(card_game): 2-5 players, one 52-card deck, 3 face-down + 3 face-up + 3 hand cards each, rest is the draw deck. Cards are numbers 0-51 (`suit = floor(c/13)`, `rank = c%13+2`, J=11..A=14).
- Phases: `swap` (everyone acts at once: swap a hand card with a face-up slot, then `ready`; hidden until all ready) → `play` → `over`. The starter is the lowest rank (from 3 up) showing in a face-up slot, else in a hand; ties go to the earlier seat (`findStarter`).
- Turn: play one card or a set of the same rank, equal or higher than the top card, from hand first, then face-up, then face-down (blind, one at a time); or `pickup` the whole pile (allowed even if a play exists). 2 plays on anything and anything plays on a 2. An **8 skips the next player** (`advance(..., skips)` in `game.ts`): each 8 in the played set skips one more active player, you can never skip yourself so with two players an 8 simply means you go again, a burn (10 / four of a kind) takes priority over skipping, a blind 8 skips too, a failed blind card never does, and the skipped ids are in `KarmaEvent.skipped` for the UI. After a 7 the next card must be **lower** than 7 (3-6), a 2 or a 10 (the article's "lower than" variant; `canPlayRank` is the single source of truth, also used by the UI to dim cards). 10 plays at any time on anything (including after a 7) and burns the pile; four of a kind on top of the pile burns it too (played at once or completed over turns). After a burn the same player leads again. After every play the hand is refilled to 3 from the deck. A too-low blind card goes onto the pile and the whole pile (including it) goes to the hand.
- Decisions where the article is silent: jokers are not used; **a 3 is invisible** (house rule, `effectiveTop` in `game.ts`: a 3 is always playable and the next play is measured against the topmost non-3 card, so 7, 3 still means "lower than 7"; a pile of only 3s counts as empty; the four-of-a-kind burn still looks at the physical top four cards). Other variants are not implemented (7 = "lower than" and 8 = "skip" are); 10s count as a starting rank; a player who burns with their last card is out and play passes on; ranks are by the order players ran out, the last player left is the loser (`score = players - rank`).
- Privacy: `getPlayerView` gives each player only their own hand; face-down cards are hidden from everyone including their owner (the view only says which slots still hold a card); the deck is a count. The pile and face-up cards are public. `lastEvent` (seq, kind, cards, burned, pickedUp, out) narrates the latest move to every client.
- `autoMove`: swap = ready; otherwise lowest legal rank (specials 2/10 last, whole set of that rank; 1 time in 4 the second-lowest, see below), else pick up; blind = first remaining slot. It reports `endsTurn` by simulating the move, so a burn (same player again) is paced like Yatzy's multi-step turns.
- **Games can loop forever under deterministic play.** With the 7 rule (and 8 skips) a fixed "always play the lowest card" strategy can circle indefinitely, e.g. a 7 that nobody can follow is picked up and led again. Measured over 500 games per size: ~1 in 500 stuck for always-lowest sets, 4-6% for single-card plays, **0 in 2000 once there is a 25% chance of the second-lowest rank** (that is what `autoMove` and the e2e strategy do; `game.test.ts` runs 600 auto-played games to guard it). Any bot or test strategy for Karma must include randomness and play sets. Humans do not loop in practice; the room's absent-player auto-play and abandoned-room TTL bound the damage anyway.
- Card animation (FLIP, in `PlayingCard.tsx`): every card with a `flip={{id, origin?}}` prop records its on-screen box after each render (module-level `lastBoxes`, keyed by card id, cleared on resize); if a card's box changed (hand re-fan, swap between hand and face-up slot, hand -> pile) it slides from the old box with the Web Animations API (320ms). A card never seen before (drawn from the deck, picked up from the pile, an opponent's hand card landing on the pile) starts from an `origin` anchor (deck / pile / that opponent's seat). The outer element is what moves, and a card's remembered box is its *layout* box (the running animation's transform is subtracted, otherwise re-renders mid-flight start bogus slides); deck/pile origins are points so cards grow out of them at their own proportions. The action column is the timer (2 parts) over the Play button (3 parts) filling everything to the right of my table cards, which sit at the left (the column is always shown; Play is only disabled off-turn, so the layout never bumps between turns). There is no Pick up button: when nothing in the active zone can be played the table picks the pile up by itself after `AUTO_PICKUP_MS` (1.1s, a client effect while `mustPickUp`; the hint says so), and a voluntary pickup is still possible by tapping the pile twice; selection lift and pile tilt live on an inner element so they never count as movement. Animations are off for the first paint and when `prefers-reduced-motion` is set (`CardFlipContext`); **tests that tap cards must use reduced motion**, otherwise Playwright waits for each sliding card to settle.
- Card sizes are numeric (px per em, card = 5em x 7em): base sizes are my cards 14, pile 17.5, deck 13.4 (>= 20% bigger than the first version at every phone height; this was measured, see below); `useCardScale` = `clamp((viewportHeight - 238) / 442, 0.72, 1.12)` fits table + hand + opponents into the screen; opponents' fonts come from `seatFont` (11 / 9.6 / 8.2 / 5.7 for 1 / 2 / 3 / 4 opponents) and with 3+ opponents their columns overlap (`overlap` prop) so bigger cards fit a narrow seat; the hand overlaps just enough to fit its width (min 24% / max 50% of a card visible); with more than `MAX_PER_ROW` (12) cards it wraps into balanced rows (`data-rows`), each overlapping the one above by half a card and drawn at 85% size, so nothing scrolls or is cut off. The deck + pile sit on the left of the table with the event/hint text and the Rules button to their right (this saved ~75px of height versus stacking the text underneath; if you change sizes, re-check that nothing overlaps at 600-860px heights with 2-5 players).
- Controls (`selection.ts`, `planTap`, unit-tested): **a rank you hold several of in the active zone: tapping any one selects all of them, tapping a selected one again deselects just that card (tap once more to add it back; no double-tap there), press Play. A card you hold once: tap selects, a slow second tap deselects, a fast second tap (`DOUBLE_TAP_MS` = 350ms, same card) plays it.** Face-down cards: tap, then Play or a fast double tap. The swap phase has a **Ready button** (`karma-ready`) and the three face-up cards float and glow (`float` prop on `PlayingCard`, CSS `.card-float` on a wrapper so FLIP boxes are unaffected; off with reduced motion); tapping one hand card and one face-up card swaps them. Tapping the table background clears the selection. Picking up: automatic when you cannot play, or tap the pile twice. A selection only resets when a new move arrives (`lastEvent.seq`). **E2E tests must wait 450ms between two taps on the same single card unless they mean a double tap**; `playSet` taps one card of the rank and presses `karma-play`; `readyUp` presses Ready.
- UI: `KarmaGame.tsx` (opponent seats, deck + pile, my face-up/face-down columns, fanned hand, rules sheet). The dock has two rows: on top my three table columns (overlapped by `MY_SLOT_OVERLAP` em) with the action column to their right, below them the full-width fanned hand (so many more hand cards are visible). Table cards are big while swapping (`tableBig`, capped by the measured width minus `ACTION_COLUMN_PX`), shrink to 62% once play starts, and grow back when my hand and the deck are empty (`endgame`); in that endgame an opponent's seat pulses and their table cards float/glow (`Seat endgame`, `TableSlots floatAll`, no text). The action column holds: turn timer (`karma-timer`, `useCountdown(game.deadline)`, red + pulse at <=10s, haptic at 10s), timer and Play button . The **pile is tappable**: first tap arms it (`data-armed`, hint "Tap the pile again to pick it up"), second tap picks it up; tapping the deck only flashes a hint, because drawing is automatic (Wikipedia has no voluntary draw), `PlayingCard.tsx` (em-scaled flat cards; `relative` is omitted when `absolute` is passed because Tailwind orders `relative` later). Fanned hand cards overlap, so only the left strip of each card is tappable (tests tap `{x: 6, y: 14}`). The plug-in hook `GameUi.resultsTitle` customises the results headline ("Karma got you!" for the loser).

- Opponent seats show their hand as a fan of small face-down cards (`HandFan`, `seat-hand-<id>` with `data-count`): beside the table cards with one opponent, under them with more.

- Narration: one short line for the latest move (`karma-event`, `describeEvent`): "Bob played 7♥", "You picked up all the cards!", "Bob flipped K♣, too low: picked up all the cards!", plus `burned 🔥`, `X skipped`, `out!`, `time ran out`. Drawing from the deck is deliberately not narrated (it happens every turn). Timeouts are not in `KarmaEvent`, so the client derives `timedOut` = the previous turn deadline had passed (`room.serverTime`). When the same player is up again (an 8 in a two-player game, or a burn) the line ends with `go again` / `plays again` instead of `skipped`, and the player gets the turn sound. My hand row is dimmed by 70% (`brightness(0.3)`) while it is not my turn in the play phase (`my-hand` `data-dimmed`). No rule hints: the hint line only carries transient text (swap instructions, selection, pile armed, deck tap).

- Win reveal: when a move has `out: true` (`lastEvent`), `KarmaGame` shows `WinReveal` for ~5s (winner: first in `finishOrder`, with confetti) or ~3.4s (later finishers): the last card turns over slowly (CSS 3D flip, `.win-card` in `index.css`), a label says "You win!" / "X wins!" / "X is out". It is `pointer-events-none`, only fires for live moves (not on reload), and with reduced motion shows the card statically without confetti. E2E: `computer.spec.ts` checks `win-reveal` (`data-winner`).

## Computer players (bots)

- A game opts in with `GameDefinition.supportsBots` (Karma only; Yatzy's `autoMove` is too basic and it has a solo mode anyway). Bots are ordinary seats in the game state: ids `bot:1..n`, names from `BOT_NAMES` (skipping names people in the room use), avatar `robot` (`packages/shared/src/game/bots.ts`). They are **not** room members for auth/chat/kick/capacity purposes (`Room.hasMember`, `memberCount`, `activeMemberIds` exclude them) but appear in `RoomView.members` with `bot: true` so the UI can name them.
- Room setting `bots` (create, `room:settings`, `RoomView.bots`). Seats are added in `Room.start()` after the people and removed on rematch (the setting stays). `room:create {gameId, bots, autoStart: true}` is the one-tap "Play the computer" flow (private room, starts at once). Total seats must fit `game.maxPlayers`; joining people count against `memberCount + bots`.
- Driving them: `Room.botDue()` / `playBots()` wake the room `botMs` after the last state change (env `BOT_DELAY_MS`, 700 in dev compose, 1000 default) and every bot that is up makes one `autoMove`. They pause while no person is connected, a room with no people closes immediately (`afterMembershipChange`) or after the TTL, and no clock is shown (`deadline: null`) while only bots are up. Bots never see anyone's private cards: they use the full server state like `autoMove` for absent players, and clients still only receive `getPlayerView`.
- Quality: Karma's `autoMove` swaps strong cards (10, 2, aces, kings...) face-up with `bestSwap` (a swap must gain >= 2 `tableValue`), then plays lowest-rank-first with a 25% second-lowest jitter. It is deliberately easy-ish; there is no difficulty setting yet.
- Web: Home shows "Play the computer" on games with `supportsBots` and a 1..(max-1) opponent picker (`RoomApi.playComputer`); the waiting room has a "Computer players" stepper and a "Start vs computer" button; Karma seats of bots show "CPU ·". Tests: `RoomManager.test.ts` (fake timers, a whole game vs 2 bots), `app.test.ts` (sockets), `e2e/tests/computer.spec.ts` (shared helpers in `karma-helpers.ts`).

## End-to-end tests (e2e/)

Standalone Playwright project (own `package.json`/lockfile, not part of the pnpm workspace) running in the official Playwright image against the compose stack: `make e2e` (= `docker compose --profile e2e run --rm e2e`, needs the stack up). It plays a full two-player Yatzy game with a mid-turn reload, plus a share-link join and kick test. Playwright version in `e2e/package.json`, `e2e/Dockerfile` must match.

## Conventions

- Server-authoritative: clients send intents only; validate with Zod, then with the game's `validateMove`.
- Live room/game state is in-memory; only users/stats are persisted in Postgres.
- Shared package is consumed as TS source (no build step). Use `import type` for types.
- Small focused commits, clear messages. Never commit `.env`.
- Keep this file updated as the project evolves.

## Running (everything runs in Docker; host needs only Docker + make)

- `make up` – build + start detached (creates `.env` from `.env.example`, detects LAN IPs) and prints URLs
- `make down` / `make logs` / `make ps` / `make urls`
- `make test` · `make lint` · `make typecheck` · `make format`
- `make migrate` · `make db-reset` (destructive) · `make db-shell` · `make shell`
- `make lock` – regenerate `pnpm-lock.yaml` after editing any package.json (then `make up` to rebuild)
- Plain `docker compose up --build --renew-anon-volumes` also works; use `HOST_LAN_IPS=<ip>` to have the server print phone URLs.
- Web: http://localhost:5173 · API: http://localhost:3000/api/healthz · DB: 127.0.0.1:5433
- Phone: open `http://<LAN-IP>:5173` (printed by `make up`). With WSL mirrored mode you may need a Windows firewall inbound rule for TCP 5173 and 3000.
- node_modules live in container-only anonymous volumes; `--renew-anon-volumes` refreshes them after dependency changes.
- File watching uses polling (`CHOKIDAR_USEPOLLING=true`) for reliable hot reload on WSL/Docker.
